# Frontend — кредитный кабинет

Vue 3 (Composition API, `<script setup>`), TypeScript, Tailwind CSS 4, Vite. Архитектура — [Feature-Sliced Design](https://feature-sliced.design/ru/).

## Запуск

Нужен Node.js 22+.

```bash
npm ci
npm run dev        # http://localhost:5173
npm run build      # проверка типов + сборка в dist/
npm run typecheck  # только проверка типов
```

Версии зависимостей зафиксированы точно в `package.json` и `package-lock.json`.

## Структура

```
src/
  app/        инициализация: main.ts, App.vue, роутер, глобальные стили и дизайн-токены
  pages/      страницы: landing, not-found, admin-* (рабочее место сотрудника)
  widgets/    крупные блоки страницы: шапка, hero, подбор, каталог, калькулятор, модалки кабинета, FAQ, футер,
              очередь и карточка андеррайтера
  features/   пользовательские действия: подбор продукта, расчёт платежа, отправка и отслеживание заявки,
              уведомления, компания, профиль, решение по задаче андеррайтера
  entities/   бизнес-сущности: credit-product (каталог, подбор), application (статусы, этапы, мои заявки),
              notification (живая лента), customer и session (сессии клиента и сотрудника), underwriting (подписи причин и факторов)
  shared/     переиспользуемое без бизнес-логики: ui-кит, lib (форматирование, финансы, ИНН), config
```

Внутри слайса — сегменты `ui/`, `model/`, `api/`, `lib/`. Наружу слайс отдаёт только то, что есть в его `index.ts`.

### Правила импортов

- Слой импортирует только из слоёв ниже: `app → pages → widgets → features → entities → shared`.
- Слайсы одного слоя не импортируют друг друга. Если двум фичам нужны общие данные — их поднимает слой ниже или страница (пример: параметры кредита `loanDraft` в `entities/application` общие для каталога, калькулятора и модалки заявки).
- Из чужого слайса импортируем только через публичный API: `@/entities/credit-product`, а не `@/entities/credit-product/ui/ProductCard.vue`.

## Дизайн

Цвета, скругления и типографика сняты с лендинга кредитов для бизнеса Альфа-Банка и заведены токенами в `src/app/styles/index.css` (`@theme`). В вёрстке используем токены (`bg-brand`, `text-ink-secondary`, `rounded-card`, `text-title`), а не произвольные hex-значения.

Фирменный шрифт закрытый, вместо него Inter (OFL), подключён локально через `@fontsource-variable/inter` — сайт не зависит от внешних CDN.

Вёрстка mobile-first, проверена на 375, 768, 1024 и 1440 px.

Витрина продуктов (`widgets/products-catalog`) — «гармошка» под любое число продуктов. На десктопе ряд — окно: раскрытая карточка не уже 30rem, рядом столько свёрнутых полосок, сколько влезает, остальные за краем (`model/useCardWindow.ts`); окно едет за раскрытой — стрелки, автопрокрутка, индикатор «03 / 24». На телефоне и планшете — лента полных карточек со свайпом.

## Сайт и рабочее место — независимые интерфейсы

Сайт для клиентов (`/`) и рабочее место сотрудников (`/admin`) друг о друге не знают:

| | Сайт | Рабочее место |
|---|---|---|
| Вход | модалка на сайте, только учётки с ролью `client` | страница `/admin/login`, только сотрудники |
| Сессия | `entities/customer`, ключ `client:session` | `entities/session`, ключ `admin:session` |
| API | `clientApi` — запросы с токеном клиента | `identityApi`, `creditApi` — с токеном сотрудника |

`http()` подписывает запрос токеном своего интерфейса (`realm: 'client' | 'staff'`), поэтому обе сессии живут одновременно, а вход и выход в одном интерфейсе не трогают другой. Ссылок между интерфейсами нет.

## Лендинг и клиентский путь

Контракт — [`docs/api/client-journey.md`](../docs/api/client-journey.md), реализация — `shared/api/client` (`clientApi`).

| Что на лендинге | Ручки бэкенда |
|---|---|
| Каталог продуктов, hero, подвал (`useProductCatalog`) | `GET /products` |
| Блок «Подберём кредит под задачу» (`widgets/product-picker`, `features/pick-product`) | не вошёл — `POST /products/recommend`; вошёл — `GET /bff/products/recommend?organization_id=…` (проверка компании и предодобренный максимум) |
| Калькулятор (`useLoanSchedule`) | `POST /products/{code}/calculate`; пока ждём ответ или бэкенд недоступен — локальная аннуитетная оценка с пометкой |
| Предодобрение в калькуляторе и мастере | калькулятор — `GET /bff/dashboard` (`pre_approved`), мастер — `pre_approved_max` из `GET /bff/products/recommend` |
| Карточка заявки в hero | `GET /bff/applications` по всем компаниям + черновики из `GET /applications` |
| Кабинет клиента (модалки, см. ниже) | `/bff/applications/{id}`, действия по заявке, `/feed`, `/news`, `/organizations/{id}/…`, `PATCH /me/profile` |
| Живые обновления (`entities/notification`, `liveFeed`) | `POST /feed/stream-ticket` → `GET /feed/stream` (SSE), `GET /feed/unread-count` |
| Модалка входа клиента (`features/customer-login`) | `POST /auth/login`, `GET /me`; демо-учётки — `GET /auth/demo-accounts` + `POST /auth/demo-login` (если на стенде `DEMO_LOGIN_ENABLED=true`) |
| Проверка входа перед заявкой | `GET /me` по сохранённому токену: истёк или нет — открывается вход |
| Подходит ли компания под продукт | `GET /products/{code}/eligibility?organization_id=…` — при выборе компании и продукта |
| Модалка заявки | `GET /organizations` → `POST /applications` → `PATCH /applications/{id}` (с `version`) → документы (`POST …/documents`, загрузка по presigned URL, `POST …/confirm`) → `GET …/completeness` → `POST …/submit` |

Все кнопки «Оформить» (шапка, мобильное меню, каталог, калькулятор) вызывают `startApplication` из `widgets/apply-flow`: вошёл — открывается заявка, нет — сначала вход, после него сразу заявка. Блока с формой на странице больше нет.

Мастер заявки (`features/submit-application`):

1. **Условия** — компания (только те, где пользователь участник) с реквизитами из банка (ОГРН, КПП, руководитель) и предупреждением, если данные расходятся с ЕГРЮЛ; затем цель кредита → «Под эту цель подходят» (подбор) → продукт → сумма с подсказкой предодобренного лимита → срок. Если компания не подходит под продукт (форма бизнеса, возраст, выручка), причины видны сразу под продуктом, «Далее» неактивна. Из блока подбора мастер открывается с уже выбранными продуктом, компанией, суммой, сроком и целью.
2. **Анкета и документы** — только если нужно: залог (продукт под залог или сумма выше порога), поля продукта по его JSON Schema (`application_fields_schema`: автокредит, ипотека, рефинансирование), документы по продукту, сумме и форме бизнеса. Файлы — как принимает бэкенд: PDF, JPG или PNG до 20 МБ, выписка по счёту — CSV.
3. **Согласия и отправка** — сводка, согласия на ПДн (152-ФЗ) и запрос в БКИ (218-ФЗ) с раскрываемым текстом, проверка комплектности, подача.

Нарушения из `completeness` и 422 на подаче показываются текстом со ссылкой «Исправить» на нужный шаг. `409 version_conflict` мастер разруливает сам: перечитывает черновик и повторяет сохранение.

Одна активная заявка на продукт у компании: если черновик уже есть (например, страницу перезагрузили посреди заявки), `POST /applications` отвечает `409 duplicate_active` с `application_id`, и мастер продолжает этот черновик — с залогом, анкетой и документами. Если заявка по продукту уже в работе, мастер пишет её номер и статус.

Ошибки бэкенда показываются русским текстом по `details.code` (`shared/api/errorMessages.ts`): `message` у бэкенда — английский текст для логов.

Карточка заявки в hero (`widgets/hero/ui/HeroApplication.vue`):

- не вошёл — пример заявки (`widgets/hero/model/content.ts`), это иллюстрация, не данные;
- вошёл — его активные заявки по всем компаниям (`entities/application`, `myApplications`): строки BFF с клиентским статусом (`client_status`) и плашкой «нужно действие» (`action_required`) плюс черновики, которых в модели чтения BFF нет. Свежая первой, остальные — переключателем «1 из N». У черновика — «Продолжить заявку»: мастер откроется с компанией и условиями черновика; у поданной — «Подробнее о заявке», открывает модалку заявки;
- вошёл, активных заявок нет — затемнённый пример, «Активных заявок нет» и кнопка «Оформить заявку».

Список перезагружается при входе и выходе, после закрытия мастера заявки и по событию `application_updated` из живой ленты.

### Кабинет клиента

Отдельной страницы нет — кабинет живёт на лендинге в модалках (`widgets/apply-flow`). Открывается из меню аккаунта в шапке и из мобильного меню; на кнопке аккаунта — бейдж непрочитанных уведомлений.

| Модалка | Что в ней | Ручки |
|---|---|---|
| Мои заявки (`features/track-application`) | заявки по всем компаниям, статус, «нужно действие» | `GET /bff/applications`, `GET /applications` |
| Заявка | статус и этап, условия, ход рассмотрения, документы (скачать), события по заявке | `GET /bff/applications/{id}`, `GET …/documents/{id}/download` |
| — решение | объяснение, «что улучшить», альтернативный продукт | из карточки BFF |
| — предложение | условия и срок действия, принять или отказаться с причиной | `POST …/offer/accept`, `POST …/offer/decline` |
| — подписание | повторный ввод пароля, итог ЭДО и выдачи (смоделированы на бэкенде) | `POST …/sign` |
| — дозапрос | что просит банк, загрузка документов, ответ банку | документы, `POST …/info-requests/{id}/answer` |
| — отмена, черновик | отмена с причиной; «Продолжить заполнение» | `POST …/cancel` |
| Уведомления (`features/read-notifications`) | события (прочитать, прочитать все, к заявке) и персональные новости | `GET /feed`, `POST /feed/{id}/read`, `POST /feed/read-all`, `GET /news`, `POST /news/{id}/read` |
| Компания (`features/manage-company`) | реквизиты из банка, сверка с ЕГРЮЛ, предодобрение, финотчётность (список и подача), участники и доверенности | `GET /organizations/{id}`, `…/financial-reports`, `…/pre-approved-offers`, `…/members`, `…/members/{id}/poa` |
| Профиль (`features/edit-client-profile`) | ФИО и должность | `PATCH /me/profile` |

Кнопки действий показываются только из `available_actions` карточки. Если действие недоступно по роли (бухгалтер без доверенности не может подписать), модалка пишет почему.

Модалка заявки обновляется по SSE; если поток недоступен — опросом раз в 5 секунд.

### Живые обновления

`entities/notification` (`liveFeed`) держит одно SSE-соединение на сессию клиента: одноразовый билет `POST /feed/stream-ticket` → `EventSource` на `stream_url`. События `feed_item` обновляют счётчик непрочитанного и ленту, `application_updated` — карточку заявки, список и hero. Переподключение — с новым билетом и `last_event_id`, с паузой от 1 до 30 секунд. Соединение открывается после входа и закрывается при выходе и на страницах без шапки.

### Запуск с бэкендом

Сайт ходит в бэкенд всегда, без моков. Dev-сервер проксирует `/api/*` на `VITE_API_PROXY_TARGET` без префикса `/api`. Против стенда из `docker compose up` (бэкенд закрыт за nginx на 80-м порту):

```bash
VITE_API_PROXY_TARGET=http://localhost npm run dev
```

- Демо-учётки без пароля появляются в модалке входа, если на стенде `DEMO_LOGIN_ENABLED=true` (`.env` корня). Иначе — вход по паролю: у клиентов из сидов он `DEMO_PASSWORD` (`Demo-2026!`).
- Документы браузер грузит напрямую в MinIO по ссылке из бэкенда (`MINIO_PUBLIC_ENDPOINT`, по умолчанию `http://localhost`).

## Админка (`/admin`)

Рабочее место сотрудника банка. Тёмное меню слева, разделы видны по правам роли, роутер проверяет то же право.

| Раздел | Право | Данные |
|---|---|---|
| Вход `/admin/login` | — | Identity API или мок |
| Обзор: цифры, заявки по дням, продукты; в mock ещё воронка, классы риска, очередь по SLA | `requests.read` | real — `GET /bff/backoffice/metrics` и очередь; mock — мок |
| Заявки: в real — очередь задач андеррайтера («Ждут решения», «Взяты в работу», «Закрытые»; причина ручного рассмотрения, срок по SLA с отметкой просрочки); в mock — все заявки с фильтрами и поиском | `requests.read` | real — `GET /bff/backoffice/queue`; mock — мок |
| Карточка заявки: компания на момент подачи, внешние источники, скоринг с вкладом факторов, решение движка, соответствие продукту, ход процесса, документы; задача андеррайтера | `requests.read`, решение — `requests.update` | real — `GET /bff/backoffice/applications/{id}`, `POST /tasks/{id}/claim`, `POST /tasks/{id}/complete`; mock — мок |
| Проверка по ИНН: досье и предварительный скоринг на сумму | `requests.read` | мок (в real — с пометкой «Демо») |
| Продукты: ставки, суммы, сроки, приём заявок | `credits.read`, правка — `credits.update` | мок (в real — с пометкой «Демо») |
| Скоринг: веса факторов, стоп-факторы, пороги, примерка на заявках | `requests.read`, правка — `admin` | мок (в real — с пометкой «Демо») |
| Пользователи и роли: создание, смена роли, удаление, матрица прав с политиками | `accounts.*`, `roles.*` | Identity API или мок |
| Профиль | любой сотрудник | Identity API или мок |

### Режимы API

Переменные — в `.env.example`.

Режим касается только рабочего места — сайт для клиентов всегда ходит в бэкенд.

- `VITE_API_MODE=mock` (по умолчанию) — админка работает в браузере, бэкенд ей не нужен. Данные хранятся в `localStorage`, кнопка «Сбросить демо-данные» на странице скоринга возвращает их к исходным.
- `VITE_API_MODE=real` — вход, профиль, пользователи и роли идут в Identity API, обзор, очередь и карточка андеррайтера — в API бэк-офиса (`shared/api/backoffice`, страницы `Backoffice*Page`, роутер выбирает их по режиму). Редактор продуктов, скоринга и проверка по ИНН остаются на моках: на бэкенде таких ручек нет, и на этих страницах это сказано плашкой «Демо» (`widgets/admin-layout`, `DemoSectionNote`).

Андеррайтер берёт задачу кнопкой «Взять в работу» и выносит решение: одобрить, контрпредложение (сумма, срок, ставка, условия), запросить данные (какие документы) или отказать — с обязательным комментарием. Процесс на бэкенде асинхронный, поэтому карточка после решения перечитывается, пока задача не закроется.

Контракты: `shared/api/identity/types.ts` и `shared/api/backoffice/types.ts` повторяют схемы бэкенда, `shared/api/credit/types.ts` — контракт мок-админки.

### Синтетические данные

`mocks/external-sources.json` — ответы ЕГРЮЛ, ЕГРИП, ФНС «Прозрачный бизнес», ГИР БО и Контура для 8 компаний и 5 ИП. Сценарии покрывают все исходы: одобрение, встречное предложение, запрос данных и отказ. ИНН и ОГРН с корректными контрольными цифрами, все лица выдуманы. Генератор — `mocks/generate.py`:

```bash
python mocks/generate.py mocks/external-sources.json
```

Скоринг (`shared/api/credit/scoring.ts`) — объяснимая балльная модель: база 50 баллов, девять факторов со шкалами, стоп-факторы, пороги одобрения. На этих данных его рекомендации совпадают с `expected_outcome` для всех 13 записей.
