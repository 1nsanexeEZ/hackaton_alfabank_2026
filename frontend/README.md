# Frontend — кредитный кабинет

Vue 3 (Composition API, `<script setup>`), TypeScript, Tailwind CSS 4, Vite. Архитектура — [Feature-Sliced Design](https://feature-sliced.design/ru/).

## Запуск

Нужен Node.js 22+.

```bash
npm ci
npm run dev        # http://localhost:5173, /api проксируется в бэкенд
npm run build      # проверка типов + сборка в dist/
npm run typecheck  # только проверка типов
npm run lint       # ESLint: ошибки, без правил оформления
```

Версии зависимостей зафиксированы точно в `package.json` и `package-lock.json`.

## Структура

```
src/
  app/        инициализация: main.ts, App.vue, роутер, глобальные стили и дизайн-токены
  pages/      страницы: landing, not-found, admin-* (рабочее место сотрудника)
  widgets/    крупные блоки страницы: шапка, hero, подбор и расчёт, каталог, модалки кабинета, FAQ, футер,
              очередь и карточка андеррайтера, отчёт проверки по ИНН, скоринг по заявкам
  features/   пользовательские действия: подбор и расчёт кредита, отправка и отслеживание заявки,
              уведомления, компания, профиль, решение по задаче андеррайтера, ведение каталога продуктов,
              проверка компании по ИНН
  entities/   бизнес-сущности: credit-product (каталог, подбор), application (статусы, этапы, мои заявки),
              notification (живая лента), customer и session (сессии клиента и сотрудника), underwriting (подписи причин и факторов),
              process (маршрут заявки по BPMN-схеме в реальном времени)
  shared/     переиспользуемое без бизнес-логики: ui-кит, lib (форматирование, финансы, ИНН), config
```

Внутри слайса — сегменты `ui/`, `model/`, `api/`, `lib/`. Наружу слайс отдаёт только то, что есть в его `index.ts`.

### Правила импортов

- Слой импортирует только из слоёв ниже: `app → pages → widgets → features → entities → shared`.
- Слайсы одного слоя не импортируют друг друга. Если двум фичам нужны общие данные — их поднимает слой ниже или страница (пример: параметры кредита `loanDraft` в `entities/application` общие для каталога, калькулятора и модалки заявки).
- Из чужого слайса импортируем только через публичный API: `@/entities/credit-product`, а не `@/entities/credit-product/ui/ProductCard.vue`.

## Дизайн

Цвета, скругления и типографика сняты с лендинга кредитов для бизнеса Альфа-Банка и заведены токенами в `src/app/styles/index.css` (`@theme`). В вёрстке используем токены (`bg-brand`, `text-ink-secondary`, `rounded-card`, `text-title`), а не произвольные hex-значения.

Фирменный шрифт закрытый, вместо него Inter (OFL), подключён локально через `@fontsource-variable/inter` — сайт не зависит от внешних CDN.

Вёрстка mobile-first, проверена на 375, 768, 1024 и 1440 px.

Витрина продуктов (`widgets/products-catalog`) — «гармошка» под любое число продуктов. На десктопе ряд — окно: раскрытая карточка не уже 30rem, рядом столько свёрнутых полосок, сколько влезает, остальные за краем (`model/useCardWindow.ts`); окно едет за раскрытой — стрелки, автопрокрутка, индикатор «03 / 24». На телефоне и планшете — лента полных карточек со свайпом.

## Сайт и рабочее место — независимые интерфейсы

Сайт для клиентов (`/`) и рабочее место сотрудников (`/admin`) друг о друге не знают:

| | Сайт | Рабочее место |
|---|---|---|
| Вход | модалка на сайте, только учётки с ролью `client` | страница `/admin/login`, только сотрудники |
| Сессия | `entities/customer`, ключ `client:session` | `entities/session`, ключ `admin:session` |
| API | `clientApi` — запросы с токеном клиента | `identityApi`, `backofficeApi` — с токеном сотрудника |

`http()` подписывает запрос токеном своего интерфейса (`realm: 'client' | 'staff'`), поэтому обе сессии живут одновременно, а вход и выход в одном интерфейсе не трогают другой. Ссылок между интерфейсами нет.

## Лендинг и клиентский путь

Контракт — [`docs/api/client-journey.md`](../docs/api/client-journey.md), реализация — `shared/api/client` (`clientApi`).

| Что на лендинге | Ручки бэкенда |
|---|---|
| Каталог продуктов, hero, подвал (`useProductCatalog`) | `GET /products` |
| Блок «Подберём кредит и рассчитаем платёж» (`widgets/loan-calculator`, `features/calculate-loan`) — подбор и калькулятор одной секцией: цель — лентой чипов, слева компания, сумма, срок и предодобрение, в центре продукты под цель строками (статус, платёж от, предодобренный максимум) в окне фиксированной высоты с прокруткой и подсказкой «ещё N ниже» — сколько бы продуктов ни было, секция не растёт; справа расчёт выбранного продукта (сумма и срок подогнаны под его рамки, что поменять, подходит ли компания) и «Оформить заявку». Компании — только продукты её сегмента. «Рассчитать» из каталога выбирает продукт и, если он не под текущую цель, переключает цель | подбор: не вошёл — `POST /products/recommend`; вошёл — ещё `GET /bff/products/recommend?organization_id=…` (проверка компании и предодобренный максимум) |
| Расчёт (`useLoanSchedule`) | гость — `POST /products/{code}/calculate` по базовой ставке; вошедший — `POST /bff/products/{code}/calculate?organization_id=` по ставке предодобрения выбранной компании: посильный максимум на выбранный срок (`max_affordable` — меньшее из предодобрения и суммы по платёжеспособности, у стартапа — по проектной оценке), причины сверх него и кнопка «Взять посильные условия». Подать больше можно — решит специалист. Пока ждём ответ или бэкенд недоступен — локальная аннуитетная оценка с пометкой. Мастер считает платёж той же ручкой |
| Продукты по сегменту компании | `Dashboard.organization.segment`: стартапу (младше 6 месяцев или без годового отчёта) — только продукты для стартапа, действующему бизнесу — без них; в калькуляторе и мастере |
| Карточка заявки в hero | `GET /bff/applications` по всем компаниям + черновики из `GET /applications` |
| Кабинет клиента (модалки, см. ниже) | `/bff/applications/{id}`, действия по заявке, `/feed`, `/news`, `/organizations/{id}/…`, `PATCH /me/profile` |
| Живые обновления (`entities/notification`, `liveFeed`) | `POST /feed/stream-ticket` → `GET /feed/stream` (SSE), `GET /feed/unread-count` |
| Модалка входа клиента (`features/customer-login`) | `POST /auth/login`, `GET /me`; демо-учётки — `GET /auth/demo-accounts` + `POST /auth/demo-login` (если на стенде `DEMO_LOGIN_ENABLED=true`) |
| Проверка входа перед заявкой | `GET /me` по сохранённому токену: истёк или нет — открывается вход |
| Подходит ли компания под продукт | `GET /products/{code}/eligibility?organization_id=…` — при выборе компании и продукта |
| Модалка заявки | `GET /organizations` → `POST /applications` → `PATCH /applications/{id}` (с `version`) → документы (`POST …/documents`, загрузка по presigned URL, `POST …/confirm`) → `GET …/completeness` → `POST …/submit` |

Все кнопки «Оформить» (шапка, мобильное меню, каталог, калькулятор) вызывают `startApplication` из `widgets/apply-flow`: вошёл — открывается заявка, нет — сначала вход, после него сразу заявка. Блока с формой на странице больше нет.

Мастер заявки (`features/submit-application`):

1. **Условия** — компания (только те, где пользователь участник) с реквизитами из банка (ОГРН, КПП, руководитель) и предупреждением, если данные расходятся с ЕГРЮЛ; затем цель кредита → «Под эту цель подходят» (подбор) → продукт → сумма с подсказкой предодобренного лимита → срок. Если компания не подходит под продукт (форма бизнеса, возраст, выручка), причины видны сразу под продуктом, «Далее» неактивна. Из блока подбора и расчёта мастер открывается с уже выбранными продуктом, компанией, суммой, сроком и целью. У стартапа для кредита на запуск бизнеса здесь же **проверка учредителя** (см. ниже): пока она не пройдена, «Далее» неактивна.
2. **Анкета и документы** — только если нужно: залог (продукт под залог или сумма выше порога), поля продукта по его JSON Schema (`application_fields_schema`: автокредит, ипотека, рефинансирование), документы по продукту, сумме и форме бизнеса. Файлы — как принимает бэкенд: PDF, JPG или PNG до 20 МБ, выписка по счёту — CSV.
3. **Согласия и отправка** — сводка, согласия на ПДн (152-ФЗ) и запрос в БКИ (218-ФЗ) с раскрываемым текстом, проверка комплектности, подача. Согласия, данные заранее в профиле, черновик берёт сам — галочки уже стоят с пометкой «дано в профиле». У ИП — необязательное согласие на решение только автоматикой (ст. 16 152-ФЗ): без него отказ и встречное предложение готовит специалист. Руководитель по реестру видит ещё и **личное согласие** на запрос своей кредитной истории — необязательное: без него банк не запросит БКИ руководителя. Остальным мастер поясняет, что согласие даёт сам руководитель. Согласие уходит до подачи, чтобы проверка данных его увидела.

Нарушения из `completeness` и 422 на подаче показываются текстом со ссылкой «Исправить» на нужный шаг. `409 version_conflict` мастер разруливает сам: перечитывает черновик и повторяет сохранение.

Одна активная заявка на продукт у компании: если черновик уже есть (например, страницу перезагрузили посреди заявки), `POST /applications` отвечает `409 duplicate_active` с `application_id`, и мастер продолжает этот черновик — с залогом, анкетой и документами. Если заявка по продукту уже в работе, мастер пишет её номер и статус.

Ошибки бэкенда показываются русским текстом по `details.code` (`shared/api/errorMessages.ts`): `message` у бэкенда — английский текст для логов.

Карточка заявки в hero (`widgets/hero/ui/HeroApplication.vue`):

- не вошёл — пример заявки (`widgets/hero/model/content.ts`), это иллюстрация, не данные;
- вошёл — его активные заявки по всем компаниям (`entities/application`, `myApplications`): строки BFF с клиентским статусом (`client_status`) и плашкой «нужно действие» (`action_required`) плюс черновики, которых в модели чтения BFF нет. Свежая первой, остальные — переключателем «1 из N». У черновика — «Продолжить заявку»: мастер откроется с компанией и условиями черновика; у поданной — «Подробнее о заявке», открывает модалку заявки;
- вошёл, активных заявок нет — затемнённый пример, «Активных заявок нет» и кнопка «Оформить заявку».

Список перезагружается при входе и выходе, после закрытия мастера заявки и по событию `application_updated` из живой ленты.

### Кабинет клиента

Отдельной страницы нет — кабинет живёт на лендинге в модалках (`widgets/apply-flow`). Открывается из меню аккаунта в шапке и из мобильного меню; на кнопке аккаунта — бейдж непрочитанных уведомлений.

| Модалка | Что в ней | Ручки |
|---|---|---|
| Мои заявки (`features/track-application`) | заявки по всем компаниям, статус, «нужно действие» | `GET /bff/applications`, `GET /applications` |
| Заявка | статус и этап, условия, ход рассмотрения, документы (скачать), события по заявке | `GET /bff/applications/{id}`, `GET …/documents/{id}/download` |
| — решение | объяснение, «что улучшить», альтернативный продукт | из карточки BFF |
| — предложение | условия и срок действия, принять или отказаться с причиной | `POST …/offer/accept`, `POST …/offer/decline` |
| — подписание | этапы договора, PDF (скачать), УИд, заёмщик, условия, график платежей, кто вправе подписать; Правила электронного взаимодействия, повторный ввод пароля. После подписи — подписанный PDF и ссылка на проверку. После выдачи договор остаётся в заявке | `GET …/contract`, `GET …/contract/document`, `GET /esign/rules`, `POST …/sign` с `offer_hash`, `document_hash`, `rules_version` |
| — дозапрос | что просит банк, загрузка документов, ответ банку | документы, `POST …/info-requests/{id}/answer` |
| — отмена, черновик | отмена с причиной; «Продолжить заполнение» | `POST …/cancel` |
| Уведомления (`features/read-notifications`) | события (прочитать, прочитать все, к заявке) и персональные новости | `GET /feed`, `POST /feed/{id}/read`, `POST /feed/read-all`, `GET /news`, `POST /news/{id}/read` |
| Компания (`features/manage-company`) | реквизиты из банка, сверка с ЕГРЮЛ (и по кнопке — что обновили из реестра), предодобрение (только после сверки с ЕГРЮЛ) — у стартапа вместо него проверка учредителя, бизнес-план с финмоделью и проектная оценка, финотчётность (список и подача), участники: добавить, сменить роль, удалить, выдать доверенность | `GET /organizations/{id}`, `POST …/verification`, `…/financial-reports`, `…/pre-approved-offers`, `GET/POST …/members`, `PATCH/DELETE …/members/{id}`, `…/members/{id}/poa`, `…/founder-prescreen`, `PUT/GET …/business-plan`, `POST/GET …/project-assessment` |
| Профиль (`features/edit-client-profile`) | ФИО и должность; «Мои согласия» — ПДн и запрос своей кредитной истории: дать, отозвать, срок, история; «Согласия компаний» — на запрос кредитной истории каждой компании | `PATCH /me/profile`, `GET/POST /me/consents`, `DELETE /me/consents/{type}`, `POST /organizations/{id}/consents`, `DELETE /organizations/{id}/consents/{type}` |

Кнопки действий показываются только из `available_actions` карточки. Если действие недоступно по роли (бухгалтер без доверенности не может подписать), модалка пишет почему.

Модалка заявки обновляется по SSE; если поток недоступен — опросом раз в 5 секунд.

### Согласия до заявки и ветка стартапа

По схеме банка согласия на ПДн и БКИ даются до заявки, сразу после выбора условий. Личные (ПДн, своя кредитная история) живут на аккаунте, согласие на запрос кредитной истории компании — на компании, его даёт любой представитель с правом подавать заявки (`entities/customer`, `personalConsents`). Руководитель ли пользователь по реестру — по `authority = registry` в списке участников.

- **Блок «Согласия для заявок»** на первом экране (`widgets/hero`, `HeroConsents`) — из `Dashboard.consents` каждой компании: что дано и до какого срока, чего нет. «Дать» открывает текст согласия; обязательные даны — черновик заявки возьмёт их сам.

- **Напоминание.** Пока заявка у банка, а руководитель согласия не дал (`Dashboard.todo` → `consent_required`, `card.consents.head_credit_bureau`), карточка на первом экране и «Мои заявки» пишут «Нужно ваше согласие на запрос кредитной истории». В модалке заявки руководитель даёт его одной кнопкой, остальные видят, кто должен его дать.
- **Стартап** (`entities/customer`, `founderPrescreen`, `FounderPrescreenPanel`). Сегмент компании и последний предскрининг — из `GET /bff/dashboard?organization_id=`. Учредитель даёт согласие и проходит проверку (`POST /organizations/{id}/founder-prescreen`): итог с причинами, срок — 30 дней. Без пройденной проверки заявку на продукт для стартапа бэкенд отклонит (`STOP_FOUNDER_PRESCREEN`), поэтому мастер не пускает дальше «Условий».
- **Бизнес-план и проектная оценка** (`features/manage-company`, `StartupProject`). В «Компании» стартапа — бизнес-план и финмодель по шаблону банка: описание, кредит, свои средства, обеспечение, гарантия господдержки и 24 месяца выручки и расходов (заполняются разом ростом от первого месяца и правятся по одному). «Оценить проект» — проектная оценка банка: пройдена — «Вам предодобрен кредит до N» и «Оформить заявку», не пройдена — причины; план изменили после оценки — предлагаем оценить заново. Заявку можно подать и без оценки — мастер подсказывает, что с ней банк скажет сумму заранее.
- **У андеррайтера** задача стартапа — «Проектная оценка»: в карточке оценка с цифрами (DSCR, свои средства, покрытие, сколько выдерживает проект) и бизнес-план, форма решения открывается с тем, что предложил бэкенд (`startup.form`), плюс оценка бизнес-плана, обеспечение и господдержка.

В подпись уходит `offer_hash` из договора: клиент подписывает то, что видел. Если предложение изменилось, пока договор был открыт (409 `offer_changed`), модалка перечитывает договор и просит подписать заново.

### Договор в PDF и электронная подпись

После «Принять предложение» бэкенд за 1–3 секунды формирует проект договора в PDF, после подписи клиента — итоговый: с листом подписания и подписью банка (`features/track-application`: `SignPanel`, `ContractStages`, `ContractDocumentBlock`).

- **Этапы** над договором: «Договор формируется» → «Ожидает вашей подписи» → «Подписан вами, подписывает банк» → «Подписан сторонами». Пока PDF формируется, карточка опрашивает `GET …/contract` раз в 2 секунды, но не дольше минуты; дольше или сбой (`status: failed`) — «Обновить».
- **Скачать** PDF можно только с токеном, поэтому файл забирает `fetch` (`httpFile` в `shared/api/http.ts`) и сохраняет `saveFile` из `shared/lib`; имя — из `Content-Disposition`. Андеррайтер скачивает договор кнопкой «Договор (PDF)» в карточке заявки.
- **Простая электронная подпись** (63-ФЗ, ст. 9): клиент отмечает «Принимаю Правила электронного взаимодействия» — это соглашение о ПЭП, текст открывается из `GET /esign/rules` — и вводит пароль. В подпись уходят `offer_hash`, `document_hash` (SHA-256 проекта PDF, который клиент видел) и `rules_version`. Проект пересобран (`document_changed`) или правила обновились (`rules_outdated`) — модалка перечитывает договор или правила и просит подписать заново.
- **Проверка по QR** — публичная страница `/verify/:id` (`pages/verify-contract`), без входа: номер, УИд, заёмщик, SHA-256, штампы подписей клиента и банка (сертификат, метка времени, время по МСК) и проверка загруженного файла (`POST /contracts/verify`). Ключ банка — демо-стенда, не квалифицированный, страница так и пишет.

Со старым бэкендом, у которого в договоре нет поля `document`, ничего из этого не показывается: договор из полей и подпись паролем, как раньше.

### Живые обновления

`entities/notification` (`liveFeed`) держит одно SSE-соединение на сессию клиента: одноразовый билет `POST /feed/stream-ticket` → `EventSource` на `stream_url`. События `feed_item` обновляют счётчик непрочитанного и ленту, `application_updated` — карточку заявки, список и hero. Переподключение — с новым билетом и `last_event_id`, с паузой от 1 до 30 секунд. Соединение открывается после входа и закрывается при выходе и на страницах без шапки.

### Анимация после входа

После успешного входа в панели (`features/customer-login`: `CustomerLoginDrawer` → `LoginSuccessTransition`) — «сборка в знак», около 1,5 с. Вход «Войти» в шапке ведёт на страницу профиля, вход после «Оформить заявку» — в мастер заявки на той же странице.

1. **Галочка** на нажатой кнопке (или на строке демо-учётки), остальное гаснет — 200 мс.
2. **Буквы собираются в знак.** Панель уходит (на телефоне — вниз). Буквы фона анимация подменяет своими копиями на тех же местах (`FloatingLetters.snapshot()`), каждая долетает до своей точки на штрихах «А» и гаснет только там; затем знак «впечатывается» — 620 мс.
3. **Профиль:** размытие темнеет до непрозрачного, под ним — переход на `/profile`; знак заливает экран красным, профиль раскрывается кругом из центра (`clip-path` у `[data-app-shell]`), белая «А» летит в логотип шапки, блоки профиля с `data-rise` поднимаются лесенкой. **Заявка:** знак сам улетает в логотип, через 300 мс открывается мастер.
4. **Логотип подсвечивается** — «долетела»: пружинит, вспышка, расходится кольцо, свечение держится и гаснет за 1,4 с. Страница к этому времени уже доступна.

Шапка к моменту полёта уже показывает вошедшего клиента: она читает сессию `customer`, которая обновляется сразу после ответа `GET /me`. Клик или Esc во время анимации — сразу финал: нужный экран открыт, поверх страницы ничего не остаётся. При `prefers-reduced-motion` полёта нет: сразу нужный экран, проявление 200 мс, логотип мягко светится. Ошибка входа и восстановление сессии по сохранённому токену анимацию не запускают.

Всё на Web Animations API и только `transform`, `opacity`, `clip-path`: правило, которое ставит анимации страницы на паузу под модалкой, и сокращение анимаций при reduced motion её не задевают. Тайминг — `features/customer-login/model/transition.ts`, геометрия знака — `model/sign.ts`.

### Запуск с бэкендом

Сайт и рабочее место ходят в бэкенд всегда, моков во фронте нет. Dev-сервер проксирует `/api/*` на `VITE_API_PROXY_TARGET` без префикса `/api`; по умолчанию — `http://localhost:8000`, бэкенд, запущенный через uv (раздел «Разработка» в [README корня](../README.md#разработка)). Переменные — в `.env.example`.

Если весь стек поднят через `docker compose up` (сайт и API на `http://localhost:8080`), в `frontend/.env.local` укажите `VITE_API_PROXY_TARGET=http://localhost:8080/api`.

- Демо-учётки без пароля появляются в модалке входа на сайте (клиенты) и на `/admin/login` (сотрудники), если у бэкенда `DEMO_LOGIN_ENABLED=true`. Иначе — вход по паролю: у клиентов из сидов он `DEMO_PASSWORD` (`Demo-2026!`).
- Документы браузер грузит напрямую в MinIO по ссылке из бэкенда (`MINIO_PUBLIC_ENDPOINT`).

Скоринг на бэкенде считает две оценки риска на одной шкале A–J — экспертную PD-модель и обученную ML-модель; зоны: A–D зелёная, E–G жёлтая, H–J красная (`policy_v8`). Данные неполные (не ответил критичный источник или мало признаков, `quality = degraded`) — карточка пишет почему, решает человек. Где зоны совпали, решает автоматика; где расходятся или риск умеренный, задача уходит человеку с видом проверки: «Проверка» (`check`) или «Спорная» (`dispute` — модели или данные расходятся). Цвет грейда в очереди и карточке — по зоне.

Андеррайтер берёт задачу кнопкой «Взять в работу» и выносит решение: одобрить, контрпредложение (сумма, срок, ставка, условия), запросить данные (какие документы) или отказать — с обязательным комментарием. Процесс на бэкенде асинхронный, поэтому карточка после решения перечитывается, пока задача не закроется.

### Маршрут заявки

Вверху карточки заявки — упрощённая схема её BPMN-маршрута (`entities/process`, `ProcessMap`). Красная точка стоит на этапе, где заявка сейчас, и едет по каждому новому переходу. Клик по этапу открывает подробности: когда начался и закончился, сколько занял и сколько было заходов, кого ждём, шаги процесса и данные карточки по этапу (`widgets/underwriter-card`, `ProcessStageDetails`): источники, оценки моделей, решение и причины, задача и срок, предложение, события этапа.

- **Схема.** `GET /workflows/{code}/diagram` — BPMN XML, разбирается `DOMParser` и кэшируется на сессию. Узлы собираются в этапы по id, одинаковым во всех маршрутах: «Подача», «Полнота», «Дозапрос», «Данные», «Стоп-факторы» (маршруты `*_v2`: сработал — сразу отказ мимо скоринга), «Залог», «Скоринг», «Решение», «Андеррайтер», «Оффер», «Подписание», «Выдача», «Отказ», «Закрыта». Шлюзы прозрачны, узел не из справочника становится отдельным этапом с названием из BPMN.
- **Раскладка.** Основная линия — самый длинный путь от подачи до выдачи. Этапы с возвратом (дозапрос) стоят над ней, финалы «Отказ» и «Закрыта» — под ней. Пропуск этапа (авторешение мимо андеррайтера) рисуется дугой. На узком экране схема прокручивается внутри панели.
- **Где заявка.** `GET /processes/{application_id}`: путь строится по `steps` (они идут по времени и с повторами; повторный заход отмечен «×2»). У завершённого процесса финал без шага («Закрыта») выводится по схеме.
- **До подачи.** Процесс начинается с подачи, а на схеме «Путь клиента — как будет» (to-be) раньше идут этапы до заявки — они встают в начало схемы (`prelude`, собирает `widgets/underwriter-card`, `usePrelude`): «Согласия» (из профиля или галочкой в заявке) → «Сверка с ЕГРЮЛ» (`GET /organizations/{id}`, `verification`) → «Предскоринг» (есть ли предодобрения у компании) → «Предодобрение» (лимит и ставка «от» по продукту заявки, `…/pre-approved-offers`); у стартапа — «Согласия» → «Учредитель» (`…/founder-prescreen`) → «Бизнес-план» (`…/business-plan`) → «Проект» (`…/project-assessment`) → «Предодобрение» (по проекту). Черновик: процесса нет, схема строится по маршруту продукта (`product_terms.workflow_code`), красная точка — на этапе до подачи, где клиент сейчас; заявку подали — процесс появляется, карточка перечитывается и точка едет дальше по маршруту.
- **Версии.** В шапке схемы — версия BPMN-маршрута («маршрут v2», у черновика — из кода маршрута) и, когда по заявке уже решали, версия кредитной политики, по которой приняли решение («политика v8»). Нумерация у них своя.
- **Обновление — опрос.** Поток SSE сотрудника шлёт события заявки, а не шаги процесса, поэтому пока процесс идёт, опрос раз в 1,5 с, пока ждёт человека или сервис — раз в 5 с, после финала опрос прекращается. На скрытой вкладке опрос на паузе. Процесс продвинулся — карточка перечитывается. После решения андеррайтера схема опрашивается сразу.

Контракты: `shared/api/identity/types.ts` и `shared/api/backoffice/types.ts` повторяют схемы бэкенда.
