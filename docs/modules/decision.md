# Модуль `decision`

## Зачем

Отвечает на вопрос **«что банк готов предложить этому заёмщику по этому продукту»**. ТЗ различает
оценку риска и кредитное решение: риск даёт `scoring` (скор, грейд, флаги), а decision добавляет
продукт, сумму и срок, внешние проверки и правила банка — **одинаковый риск даёт разные условия на
разных продуктах**. Итог не бинарный: одобрить как просили, предложить другие условия, запросить
информацию, отдать андеррайтеру или отказать — с альтернативным продуктом.

Эксперты вебинара 21.10 просили, чтобы **банк понимал, почему предложено именно это**: каждое
проверенное правило попадает в `rule_trace` с цифрами, лимиты видны по отдельности, ставка — по
шагам. Клиент видит только итог и человеческое объяснение без внутренних цифр.

**Не отвечает за:** оценку риска (берёт готовый скор), статусы заявки (process, applications),
очередь андеррайтера (process).

## Язык модуля

| Термин | Значение |
|---|---|
| Кредитная политика (`CreditPolicy`) | версионированный набор правил банка: встроенная `policy_v10`, `policy_v1`–`policy_v9` — для истории и отката; поверх них — версии админа (`policy_v10.1`…) |
| Стоп-фактор | условие, при котором отказ без вариантов |
| Мягкий триггер | не отказ, а повод показать заявку андеррайтеру (policy_v3) |
| Матрица грейд × сумма | по корзине грейдов: до какой суммы решает автоматика, до какой — человек, выше — отказ (policy_v3) |
| Лимит | наибольшая сумма, которую банк готов дать: минимум из ограничений (в policy_v3 — семи, с `binding`) |
| LTV | доля стоимости залога, под которую банк даёт деньги |
| Платёжеспособность | платёж ≤ 40% свободного денежного потока |
| Маршрутизация | правила «решать автоматически или отдать андеррайтеру» |
| Трасса правил (`rule_trace`) | что проверено, сработало ли и почему — для аудита и андеррайтера |
| Причина (`ReasonCode`) | внутренний код решения; у каждого — текст для клиента |
| Предскрин учредителя (`FounderPrescreen`) | проверка личной кредитной истории учредителя стартапа до заявки: `passed` / `failed`, действует 30 дней (policy_v4) |
| Проектная оценка (`ProjectAssessment`) | оценка стартапа по бизнес-плану и финмодели до заявки: `passed` — предложение `STARTUP` с `basis = project`, действует 30 дней (#156) |

## Устройство

- `domain/` — чистый Python: вход политики (`DecisionInput`), `CreditPolicy.decide(inp, key_rate=…)`
  без IO и без `now()`, итог `PolicyDecision`, запись решения `DecisionResult`.
- `application/input_builder.py` — собирает `DecisionInput` из фасадов соседей: заявка и копия
  условий продукта (`applications.get_scoring_input`), дозапросы (`applications.get_card`),
  ЕГРЮЛ/ФНС/БКИ, ГИР БО, Контур, БКИ руководителя и прогноз по выписке
  (`enrichment.get_snapshot`), грейд, PD и флаги
  (`scoring.get_result`), программа господдержки и eligibility альтернатив (`products`), для
  продукта стартапа — предскрин учредителя на дату подачи (своё хранилище). Грейд
  скоринга переводится на шкалу политики (`on_scale`): результат scorecard_v1 (A–E) для policy_v3
  — A→B, B→D, C→F, D→H, E→J, результат PD-модели (A–J) для policy_v1/v2 — попарно в A–E.
- `application/founder_prescreen.py` — предскрин учредителя стартапа (раздел
  [Ветка стартапа](#ветка-стартапа-policy_v4-и-предскрин-учредителя)).
- `application/project_assessment.py` — проектная оценка стартапа и предложение по ней (раздел
  [Проектная оценка](#ветка-стартапа-проектная-оценка-до-заявки)).
- `infrastructure/config/policy_v10.yaml` (встроенная), `policy_v1.yaml`–`policy_v9.yaml` — пороги и
  коэффициенты, `explanations_ru.yaml` — тексты
  для клиента. Оба файла проверяются Pydantic-схемой при старте (`config_loader.py`): нет грейда,
  кода причины, текста или в шаблоне неизвестная подстановка → `PolicyConfigError`, приложение не
  стартует. Логика правил — в коде, цифры — в YAML: калибровка меняется без правки кода.
- `config.py` — ночной пакет предодобрения; ключевая ставка — общий `KEY_RATE` (`src/core/config.py`)
  (`DECISION_PRE_APPROVAL_REFRESH_*`, см. [Runtime](#runtime-команды-события-api)).

## Версии политики админа

Админ меняет политику через API, а не правкой YAML: стоп-факторы, лимиты, ценообразование,
маршрутизацию, стратегию (мягкие триггеры, матрица грейд × сумма, зоны двух моделей), требования
закона — всё, что есть в `policy_v10.yaml`. Устроено так же, как версии PD-модели в
[scoring](scoring.md#версии-pd-модели).

- **Встроенная версия** `policy_v10` — из YAML, только читается. В БД её нет: она действует, пока
  ни одна версия админа не активна.
- **Версии админа** лежат в `decision_policy_versions` (`decision_0005`). Код —
  `<встроенная>.<n>`: `policy_v10.1`, `policy_v10.2`… Номер — следующий после наибольшего занятого.
- **Статусы** `draft → active → archived`. Черновик — копия любой версии, в том числе встроенной
  или архивной. Править (`PUT`) и удалять можно только черновик. Активировать можно черновик или
  архивную версию, это и есть откат; прежняя активная уходит в архив. Активной бывает одна версия:
  частичный уникальный индекс `uq_decision_policy_versions_active`, гонку двух активаций
  проигравший получает как 409.
- **Вернуть встроенную** — `POST /decision/policies/policy_v10/activate`: активная версия из БД
  уходит в архив, снова действует YAML.
- **Документ версии** (`body`) — тот же документ, что YAML, в JSON: Decimal строками, пустые поля
  опущены. `version` внутри документа всегда равен коду версии: он пишется в
  `decision_results.policy_version`. JSONB переставляет ключи, поэтому `routing.flags`
  проверяются в постоянном порядке (`_ROUTING_FLAGS`), а не в порядке ключей документа.
- **Проверка** общая с YAML: `parse_policy` в `infrastructure/config_loader.py`. Ошибки
  собираются списком: 422 `validation_error`, в `details.errors` — `[{path, message}]`, например
  `{"path": "routing.flags.mass_address", "message": "нет текста для кода причины ROUTE_NOT_EXPLAINED"}`.
  Тексты для клиента (`explanations_ru.yaml`) через API не правятся: код причины без текста —
  422. Грейд вне шкалы, дыра в матрице двух моделей, неизвестный статус ЕГРЮЛ, флаг или форма —
  тоже 422.
- **Аудит:** `created_by/at`, `updated_at`, `activated_by/at`, `based_on`, `comment`.

### Какой версией решается заявка

`ActivePolicyProvider` на каждую команду (`CheckStopFactors`, `MakeDecision`, `RecordManualDecision`),
событие clients, проход ночного пакета, запрос проектной оценки и сид делает один короткий запрос
«какая версия активна». Собранная политика кэшируется в процессе по коду версии: версии неизменны,
поэтому кэш не протухает. Новая версия действует со следующей команды; прежние решения остаются на
своей `policy_version`. Ключевая ставка — из настроек (`KEY_RATE`), в документ не входит.

Если политику активировали между `CheckStopFactors` и `MakeDecision` одной заявки, команды пройдут
на разных версиях. Это допустимо: у каждого решения в журнале видна своя версия.

### Примерка

`POST /decision/policies/{version}/preview?limit=50` решает заново последние `limit` заявок с
автоматическим решением (по заявке — последнее авторешение; ручные не берутся) и ничего не пишет.
Порядок как в процессе: сначала стоп-факторы, затем решение. Это примерка, а не точное
воспроизведение: вход собирается заново `DecisionInputBuilder` из текущих данных (заявка,
последний снимок обогащения и результат скоринга, каталог продуктов) с текущей ключевой ставкой.
Поэтому `after` может отличаться от `before` и при той же политике, если данные с тех пор
поменялись.

В ответе по каждой заявке — `before` (сохранённое решение: исход, коды причин, его
`policy_version`) и `after` (как решила бы примеряемая версия); сводка `changed` (другой исход или
другие коды причин), `outcome_changed` и переходы исходов `[{from, to, count}]` — только непустые.
Заявка, вход которой уже не собрать (её или продукта нет), считается в `skipped`.

## Правила `policy_v1` по порядку

Первое терминальное правило останавливает конвейер; всё проверенное — в `rule_trace`.

### 1. Стоп-факторы → `REJECT`
**Зачем:** есть ситуации, в которых кредит не выдают ни на каких условиях — нет смысла считать лимит.

| Условие | Причина |
|---|---|
| статус по ЕГРЮЛ `liquidating` / `liquidated` | `STOP_LIQUIDATION` |
| статус `bankrupt` | `STOP_BANKRUPTCY` |
| руководитель дисквалифицирован (ФНС) | `STOP_DISQUALIFIED_HEAD` |
| просрочка (текущая или за 12 мес.) **> 90** дней (БКИ) | `STOP_OVERDUE_90` |
| грейд **E** | `STOP_GRADE_E` |

Записываются все сработавшие стоп-факторы, альтернатива не предлагается.

### `policy_v2`: стоп-факторы новых источников

Из таблицы стоп-факторов общей схемы — там, где у нас есть данные. Пороги стартовые, все в
`policy_v2.yaml`. Источник не ответил или не запрошен → проверка в трассе «не выполнена», а
решение уходит на ручную проверку по `ROUTE_SOURCES_FAILED` (сбой) либо идёт дальше (нет согласия
руководителя).

| Условие | Источник | Ключ YAML | Причина |
|---|---|---|---|
| текущая просрочка компании **≥ 30** дней | БКИ | `current_overdue_days: 30` | `STOP_CURRENT_OVERDUE` |
| текущая просрочка руководителя **≥ 30** дней | БКИ руководителя (с его согласия) | `current_overdue_days: 30` | `STOP_HEAD_OVERDUE` |
| есть решения о приостановлении операций по счетам | ФНС | `account_blocks: true` | `STOP_ACCOUNT_BLOCKS` |
| недоимка **> 300 000 ₽** | ФНС | `tax_arrears_above` | `STOP_TAX_ARREARS` |
| есть сообщения о банкротстве | Контур | `bankruptcy_messages: true` | `STOP_BANKRUPTCY_MESSAGE` |
| исполнительные производства **> 10%** годовой выручки | Контур | `enforcement_revenue_share` | `STOP_LARGE_ENFORCEMENT` |
| иски к компании **> 20%** годовой выручки | Контур | `lawsuits_revenue_share` | `STOP_LARGE_LAWSUITS` |
| отрицательный собственный капитал в последнем периоде | ГИР БО | `negative_equity: true` | `STOP_NEGATIVE_EQUITY` |
| адрес массовой регистрации (в v1 — ручная проверка) | ЕГРЮЛ | `mass_address: true` | `STOP_MASS_ADDRESS` |
| основной ОКВЭД из стоп-листа банка (класс `92` — азартные игры) | ЕГРЮЛ | `okved_classes` | `STOP_FORBIDDEN_OKVED` |

Годовая выручка для долевых порогов — последний период ГИР БО, иначе ФНС, иначе отчёт клиента.

Маршрут v2: недоимка больше нуля, но не выше стоп-порога → `ROUTE_TAX_ARREARS` (`routing.tax_arrears`).
Выручка ГИР БО ниже заявленной по-прежнему ловится флагом `revenue_mismatch` через дозапрос выписки.

Чего из таблицы схемы в v2 не было — экстремисты и 115-ФЗ — добавила policy_v6, остальное
(реорганизация и исключение из реестра, недостоверность сведений, массовый руководитель, срок работы,
стоп-лист банка) — policy_v7, см. [Стоп-факторы до модели](#стоп-факторы-до-модели-policy_v7).

### `policy_v3`: стратегия решения

«Стратегия решения» общей схемы на шкале A–J PD-модели (`scoring`, `pd_model_v2`). Стоп-факторы и
дозапрос — как в v2; грейд больше не стоп-фактор и не маршрут (`stop_factors.grades: []`,
`routing.grades: []`) — его отсекает матрица. Всё — в `policy_v3.yaml`.

**Порядок после стоп-факторов и дозапроса:**
1. ставка из компонент и лимиты — считаются всегда, андеррайтер видит их и в ручном решении;
2. маршруты v2 (сумма выше автоматики продукта, расхождения, сбой источников, массовый адрес);
3. мягкие триггеры → `ROUTE_SOFT_TRIGGER`, список — в `decision.triggers: [{code, detail}]`;
4. матрица грейд × сумма → одобрить (дальше лимиты) / `ROUTE_RISK_MATRIX` / `STOP_RISK_MATRIX`.
   Сбой источников и мягкие триггеры идут **раньше** матрицы: при них решает человек, а не отказ;
5. исход — как в v1: в пределах лимита — APPROVE, иначе COUNTER_OFFER (сначала удлиняем срок в
   рамках продукта, потом снижаем сумму), ниже минимума продукта — REJECT.

**Мягкие триггеры** (`strategy.soft_triggers`):

| Триггер | Условие | Источник |
|---|---|---|
| `tax_arrears` | недоимка больше нуля, но не выше стоп-порога 300 000 ₽ (в v2 это был `ROUTE_TAX_ARREARS`) | ФНС |
| `head_change` | руководитель сменился меньше **6** мес. назад (запись в ЕГРЮЛ позже регистрации) | ЕГРЮЛ, `head_since` |
| `turnover_spike` | поступления за последние **3** мес. выписки в среднем больше **1,5 ×** среднего за прежние месяцы | выписка |

Нет данных (ФНС не ответила, ЕГРЮЛ не сообщил дату, выписки нет) — триггер в трассе «не
выполнен». Смену руководителя Контур в наших данных не отдаёт — смотрим ЕГРЮЛ.

**Матрица грейд × сумма** (`strategy.risk_matrix`):

| Корзина | Автоматика до | Ручная до | Выше |
|---|---|---|---|
| A–C | 50 млн | без ограничения | — |
| D–E | 15 млн | 50 млн | отказ |
| F–G | 5 млн | 20 млн | отказ |
| H–J | — | 3 млн | отказ |

**Лимит** — минимум из ограничений, `limits.binding` — какое дало минимум:

| Ограничение | Как | Причина |
|---|---|---|
| `by_product` | максимум продукта | `LIMIT_BY_PRODUCT` |
| `by_revenue` | k(грейд) × годовая выручка: A 0,5 · B 0,45 · C 0,4 · D 0,3 · E 0,25 · F 0,2 · G 0,15 · H 0,1 · I 0,05 · J 0 | `LIMIT_BY_REVENUE` |
| `by_turnover` | 0,5 × обороты по счёту за год по выписке; выписки нет — не ограничиваем | `LIMIT_BY_TURNOVER` |
| `by_capacity` | платёж ≤ 40% свободного потока, как в v1 | `LIMIT_BY_PAYMENT_CAPACITY` |
| `by_grade` | максимум на грейд: A 60 · B 50 · C 40 · D 30 · E 20 · F 10 · G 5 · H 2 · I 1 · J 0 млн | `LIMIT_BY_GRADE` |
| `by_group` | 100 млн − остаток долга по действующим кредитам (БКИ). Связанных компаний в данных нет — группа это сама компания | `LIMIT_BY_GROUP` |
| `by_ltv` | для залоговых — как в v1 | `LIMIT_BY_LTV` |

**Ставка** = фондирование + ожидаемые потери + капитал + маржа, в коридоре продукта, потолок
господдержки — как в v1:
- фондирование = ключевая + спред 1,0 п.п.;
- ожидаемые потери = PD × LGD × 100: LGD 0,45 без залога, 0,25 при покрытии залогом ≥ 1;
- капитал 2,0 п.п., маржа 3,5 п.п.;
- у результата scorecard_v1 PD нет — берём осторожную 10% (`pd_if_unknown`).

Коридор продукта и потолок господдержки приходят из каталога уже сдвинутыми за ключевой: ставки
каталога заданы при `CATALOG_KEY_RATE` (16,50%), products сдвигает их на `KEY_RATE −
CATALOG_KEY_RATE` (при 14% — на −2,5 п.п., [products](products.md#ставки-за-ключевой)). Поэтому
ставка двигается вслед за ключевой целиком, а не упирается в пол коридора. Коридор заявки — из
снимка условий на дату подачи, фондирование — по ключевой на момент решения.

Разбивка — в `decision.rate_breakdown: {funding, expected_loss, capital, margin, total}`, `total` —
итог после коридора.

**Обеспечение:** поручительство собственника в `offer.conditions` для грейдов F–G и сумм больше
20 млн (`strategy.guarantee`), если у продукта своего поручительства нет.

### Ветка стартапа: `policy_v4` и предскрин учредителя

**Зачем:** у компании младше полугода или без годовой отчётности нет ни оборотов, ни выручки —
скоринг и лимиты по ним о проекте ничего не скажут. Ветка «нет бизнеса» общей схемы: личный
скоринг учредителя (предскрин) → прошёл → проектная оценка андеррайтером; не прошёл — «отказ
(стартап)». v4 = v3 + ключ `startup` в YAML; для остальных продуктов решения и трасса как в v3.

**Предскрин** — до заявки, по кнопке в кабинете (`FounderPrescreenUseCase`,
`application/founder_prescreen.py`):
1. учредитель — участник компании, чьё ФИО совпало с руководителем по реестру
   (`clients.get_registry_head`); такого нет → 422 `founder_not_found`;
2. нужно его действующее согласие `credit_bureau_personal` (`identity`); нет → 422
   `consent_required`, в БКИ не ходим;
3. запрос в БКИ физлица сразу, без заявки и без кеша (`enrichment.lookup_person_bureau`), оценка —
   `scoring.prescreen_person`: правила `prescreen_v1`, см.
   [scoring](scoring.md#предскрин-учредителя-prescreen_v1). Бюро не ответило → 503, ничего не
   сохраняется;
4. результат — новая запись, действует последняя; срок — 30 дней (`PRESCREEN_VALID_DAYS`), как у
   предодобрения. `failed` — это «отказ (стартап)»: клиент видит причины (`reasons[].message`) без
   порогов.

**Правила v4** (`startup.products: [STARTUP]`):
- стоп-фактор `stop.founder_prescreen`: заявка на продукт стартапа без пройденного предскрина,
  действовавшего на дату подачи (`submitted_at`) → REJECT `STOP_FOUNDER_PRESCREEN`, альтернативы
  нет. Статус собирает `input_builder` по последнему предскрину компании:

  | `founder_prescreen` | Когда | Итог |
  |---|---|---|
  | `passed` | пройден и действовал при подаче | дальше по правилам |
  | `failed` | не пройден | `STOP_FOUNDER_PRESCREEN` |
  | `expired` | истёк к подаче | `STOP_FOUNDER_PRESCREEN` |
  | `missing` | предскрина не было | `STOP_FOUNDER_PRESCREEN` |

  Клиенту: «Для кредита на запуск бизнеса нужна действующая проверка личной кредитной истории
  учредителя», подсказка — пройти проверку в кабинете и подать заявку снова;
- матрица грейд × сумма для продукта стартапа не применяется — в трассе `strategy.risk_matrix`
  «вместо матрицы — проектная оценка андеррайтером». Грейд стартапа считается по карте
  `new_client` без оборотов и о проекте ничего не говорит;
- `auto_decision_limit` у `STARTUP` — 0, поэтому с пройденным предскрином заявка всегда уходит на
  `MANUAL_REVIEW` (`ROUTE_AMOUNT_OVER_AUTO_LIMIT`). Маршрут `startup_v1` даёт андеррайтеру форму
  `project_assessment`: бизнес-план, финмодель, обеспечение, господдержка. Клиент видит этап
  «Проектная оценка». Ставка и лимиты посчитаны как в v3 — андеррайтер видит их рядом с проектом.

Остальные стоп-факторы v2 — статус по ЕГРЮЛ, просрочки, ФНС, Контур — для стартапа действуют как
обычно.

### Ветка стартапа: проектная оценка до заявки

**Зачем (#156):** на общей схеме у стартапа предскрин учредителя → бизнес-план и финмодель →
проектная оценка → «вам предодобрен кредит» → общий путь заявки. Раньше после предскрина сразу шла
заявка, а проектная оценка была только финальным ручным решением. Теперь банк оценивает проект до
заявки, клиент видит «предодобрено до N», а андеррайтер по заявке подтверждает уже заполненную
оценку.

**Проектная оценка** — по кнопке в кабинете (`AssessProjectUseCase`,
`application/project_assessment.py`):
1. бизнес-план и финмодель — из кабинета компании (`clients.get_business_plan`, шаблон —
   [clients](clients.md#бизнес-план-стартапа)); нет → 422 `business_plan_required`;
2. продукт — из `startup.products` политики, со `startup_only` и подходящий компании по
   eligibility (сейчас `STARTUP`); нет → 422 `product_not_eligible`: компании с оборотами
   кредит на запуск не предлагаем;
3. предскрин учредителя — последний, `passed` и действует сейчас; нет — правило
   `founder_prescreen` scoring не пройдено, клиент видит причину;
4. оценка — `scoring.assess_project` (правила `project_v1`, см.
   [scoring](scoring.md#проектная-оценка-стартапа-project_v1)): запрошенная сумма, срок плана в
   рамках продукта, платёж — по **верхней ставке коридора** продукта (у `STARTUP` 26%):
   предодобренная сумма выдерживает любую ставку, которую назначит андеррайтер;
5. прошла → предложение по продукту, `basis = project`, на 30 дней: сумма — сколько выдерживает
   проект, не больше максимума продукта, вниз до шага суммы политики (`limits.amount_step`);
   ставка от — база продукта, срок до — максимум продукта. Меньше минимума продукта — предложить
   нечего: оценка `failed` с причиной `product_amount`. Не прошла → проектное предложение
   снимается;
6. оценка — новая запись (`decision_project_assessments`), действует последняя, 30 дней
   (`PROJECT_VALID_DAYS`); в ней ревизия бизнес-плана, по которой оценивали, и цифры для
   андеррайтера (`ProjectFigures`: запрос, срок, ставка, поток, платежи, DSCR, доля своих,
   покрытие, сколько выдерживает проект). В outbox — `PreApprovedOffersUpdated`: клиенту в ленту
   «Для вас есть предодобренные предложения».

Предложения по оценке без заявки (`estimate`) и проектные живут раздельно: пересчёт предодобрения
по событиям clients (`replace_for_organization`) не трогает проектное, проектная оценка
(`replace_project_offers`) — предложения по оценке. Ночной пакет продлевает только предложения
по оценке (`organizations_expiring_by` проектные не считает): проектное пересчётом не продлить,
только новой проектной оценкой. Поменяли бизнес-план — прежняя оценка остаётся до нового запуска;
что она отстала, видно по `plan_revision`.

**Заявка после оценки.** Продукт `STARTUP` по-прежнему решает андеррайтер (`auto_decision_limit` 0,
маршрут `startup_v2`, форма `project_assessment`). Карточка андеррайтера (bff,
`UnderwriterCard.startup`) несёт оценку с цифрами, бизнес-план и **заполненную форму**: оценка
пройдена и действовала при подаче, сумма в пределах предложения — «одобрить» на запрошенную
сумму, бизнес-план `acceptable`, обеспечение и господдержка — из финмодели; андеррайтер
подтверждает проект. Сверх предложения — встречное предложение на предодобренную сумму:
проект большего не выдерживает по DSCR, своим средствам или покрытию, но может выдержать меньше,
и решать это человеку — бизнес-план мог измениться, а предложение у клиента на руках. Оценка не
пройдена или истекла — «отказать» с причинами оценки; андеррайтер вправе не согласиться.

Правило политики для заявки на `STARTUP` по проектной оценке — следующим шагом #156, новым ключом
в `policy_v7.yaml` поверх полного перечня стоп-факторов (#146):
- оценка не пройдена и действовала при подаче → отказ, как при непройденном предскрине:
  причины клиент уже видел в кабинете;
- в пределах предложения → ручная проверка (`check`): андеррайтер подтверждает проект;
- сверх предложения → ручная проверка (`check`) с встречным предложением в форме: отказ
  автоматом отнял бы у человека решение о меньшей сумме;
- оценки нет или истекла → ручная проверка, как до #156: бизнес-план и финмодель обязательны в
  документах заявки, андеррайтер оценивает проект сам (S-9).

До этого правила всё, что выше, решает андеррайтер по заполненной форме; исходы политики для
`STARTUP` не меняются.

### Две модели: `policy_v5`

**Зачем:** скоринг считает на каждой заявке две оценки риска — экспертную PD-модель и обученную
ML-модель ([scoring](scoring.md#ml-модель-ml_logreg_v1)), обе на шкале A–J. Где модели согласны,
решает автоматика; где расходятся или видят умеренный риск, решает андеррайтер — и видит обе
оценки. v5 = v4, в YAML вместо `strategy.risk_matrix` — `strategy.two_models`.

**Зоны** по грейду, одинаковые для обеих моделей: green A–D (PD < 2,75%), yellow E–G (2,75–9%),
red H–J (от 9%). **Матрица** (строка — PD-модель, столбец — ML-модель):

| PD ↓ / ML → | green | yellow | red |
|---|---|---|---|
| **green** | одобрение | проверка | спорная |
| **yellow** | проверка | проверка | спорная |
| **red** | спорная | спорная | отказ |

- **одобрение** — дальше лимиты как прежде: APPROVE или COUNTER_OFFER;
- **проверка** (`ROUTE_MODELS_CHECK`) — `MANUAL_REVIEW`, вид `check`;
- **спорная** (`ROUTE_MODELS_DISAGREE`) — `MANUAL_REVIEW`, вид `dispute`;
- **отказ** (`STOP_MODELS_HIGH_RISK`) — REJECT. Исключение: данные неполные (сбой источников) —
  модели посчитаны не на всём, решает человек (`dispute` по `ROUTE_SOURCES_FAILED`);
- оценки ML нет — `ROUTE_ML_UNAVAILABLE`, `dispute`: результат до `scoring_0003` или модель не
  применяется — у компании нет выручки (`ml_not_applicable = "no_revenue"`, [scoring](scoring.md#ml-модель-ml_logreg_v1)).
  В трассе: «ML-модель не применяется: у компании нет выручки, модель обучена на действующих
  компаниях».

**Поверх матрицы**, в прежнем порядке правил:
1. стоп-факторы → REJECT при любых моделях;
2. выручка не подтверждена, дозапроса ещё не было → REQUEST_INFO;
3. расхождения в данных — верификация, выручка после дозапроса, сбой источников — делают заявку
   спорной;
4. мягкие триггеры и сумма выше `auto_decision_limit` продукта — не меньше проверки.

Мягкие триггеры не спасают от отказа, если обе модели в красной зоне. Для продукта стартапа матрица
не применяется, как в v4 (проектная оценка).

**Вид ручной проверки** — `review_kind` в контракте (`decision/facade.py`): `dispute`, если среди
причин есть `ROUTE_MODELS_DISAGREE`, `ROUTE_ML_UNAVAILABLE`, `ROUTE_SOURCES_FAILED`,
`ROUTE_VERIFICATION_MISMATCH`, `ROUTE_MASS_ADDRESS` или `ROUTE_REVENUE_MISMATCH`, иначе `check`.
Вид выводится из кодов причин, поэтому миграции не нужно, и он есть у решений любой версии.

Трасса: правило `strategy.two_models`, например «PD-модель: грейд A (PD 0.41%) — зелёная;
ML-модель: грейд C (PD 1.39%) — зелёная → одобрение, дальше лимиты». Клиент про модели не узнаёт:
тексты причин общие («Специалист банка посмотрит заявку перед решением»).

### 2. Дозапрос → `REQUEST_INFO`
**Зачем:** расхождение выручки с ФНС не повод отказывать — повод попросить подтверждение.
Флаг скоринга `revenue_mismatch`, а закрытого дозапроса с `bank_statement` ещё не было (видно по
`applications.get_card().info_requests`, статус не `open`) → запросить выписку: «Подтвердите
выручку выпиской по счёту за 6 месяцев». Дозапрос уже был и выписка выручку не подтвердила —
идём дальше, маршрутизация отдаст заявку андеррайтеру.

### 3. Ставка
**Зачем:** эксперты просили учитывать «текущую ситуацию в кредитовании» — ключевая ставка ЦБ
сдвигает цену денег для банка.

```
rate = clamp(rate_base + premium(грейд) − discount(залог) + (key_rate − key_rate_reference),
             rate_base, rate_max)
GOV_SUPPORT: rate = min(rate, support_program.rate_cap), если компания в реестре МСП
             и её класс ОКВЭД — в списке программы
```

| Параметр | Значение |
|---|---|
| надбавка за грейд | A 0 · B +1,5 · C +3,5 · D +6,0 п.п. |
| скидка за залог | −1,5 п.п. при покрытии (стоимость залога / сумма) ≥ 1 |
| `key_rate_reference` | 16,50% — опорная ключевая policy_v1/v2; с policy_v3 ставка на неё не смотрит |
| `KEY_RATE` | env, общий с каталогом, по умолчанию 14,00% (решение Банка России от 23.10.2026). **Сверять с cbr.ru** |

Каталог сам сдвигает коридор за ключевой (см. policy_v3), так что policy_v1/v2 при `KEY_RATE ≠
CATALOG_KEY_RATE` сдвинули бы ставку дважды: они остались для golden-тестов на зафиксированных
входах.

Ставка считается до лимита: от неё зависит платёжеспособность.

### 4. Лимит
**Зачем:** сумма ограничена тем, сколько бизнес реально может обслуживать, а не только продуктом.

```
limit = min(
    product.amount_max,                                   # LIMIT_BY_PRODUCT
    k(грейд) × годовая выручка,                            # LIMIT_BY_REVENUE
    LTV(тип залога) × стоимость залога,                    # LIMIT_BY_LTV — только залоговые продукты
    сумма, при которой платёж ≤ 40% свободного потока,     # LIMIT_BY_PAYMENT_CAPACITY
)
```

| Параметр | Значение |
|---|---|
| k(грейд) | A 0,5 · B 0,4 · C 0,25 · D 0,15 |
| выручка для k | меньшая из заявленной (последний годовой отчёт) и по ФНС — консервативно |
| LTV | недвижимость 0,7 · транспорт 0,6 · оборудование 0,5 · товары 0,3 |
| свободный поток | **по выписке, если она есть**: средний месячный чистый поток − платежи по кредитам из БКИ; иначе по отчёту: (выручка − расходы) / 12 − платежи по БКИ |
| нет расходов в отчёте | принимаем 80% выручки — допущение пишется в `rule_trace` |
| платёж | аннуитет, та же формула, что `products.calculate_payment` |

Банк видит все четыре лимита отдельно (`limits.by_revenue`, `by_ltv`, `by_capacity` при запрошенном
сроке) — понятно, какое ограничение сработало.

### 5. Маршрутизация → `MANUAL_REVIEW`
**Зачем:** автоматика решает только то, в чём уверена; остальное — андеррайтеру с готовой трассой.

| Условие | Причина |
|---|---|
| сумма > `auto_decision_limit` продукта (у `MORTGAGE` — 0, т.е. всегда) | `ROUTE_AMOUNT_OVER_AUTO_LIMIT` |
| грейд **D** | `ROUTE_GRADE_D` |
| флаг `verification_mismatch` (или статус верификации `mismatch`) | `ROUTE_VERIFICATION_MISMATCH` |
| флаг `revenue_mismatch` после дозапроса выписки | `ROUTE_REVENUE_MISMATCH` |
| флаг `bureau_unavailable` или не ответил внешний источник (ЕГРЮЛ, ФНС, БКИ; в v2 — и ГИР БО, Контур, БКИ руководителя); нет результата скоринга | `ROUTE_SOURCES_FAILED` |
| флаг `mass_address` | `ROUTE_MASS_ADDRESS` |

`thin_file` **не маршрутизирует** (только −10 баллов в скоринге) — иначе молодой ИП (S-2) никогда
не получит встречное предложение. Ставка и лимиты для ручного решения всё равно посчитаны.

### 6. Исход
- запрошенная сумма в пределах лимита, срок в рамках продукта, платёж проходит → **APPROVE** как
  просили;
- иначе **COUNTER_OFFER**: сумма = меньшее из запрошенной и лимитов, округлённое **вниз до
  10 000**; срок — кратчайший от запрошенного в рамках продукта, при котором платёж проходит
  платёжеспособность (если не проходит и на максимальном сроке — сумма по платёжеспособности на
  максимальном сроке). Клиенту объясняем ограничение, которое определило сумму;
- сумма ниже минимума продукта → **REJECT** (`LIMIT_BELOW_PRODUCT_MIN`) с альтернативой: есть
  залог, а продукт беззалоговый → `SECURED`; ожидается кассовый разрыв → продукт под него;
  иначе `OVERDRAFT`, если лимит дотягивает до его минимума.

Оффер: схема погашения — первая из продукта, условия (залог, поручительство, целевое
использование, кассовый разрыв), платёж считает `products.calculate_payment`, срок действия 7 дней.

### Кассовый разрыв в решении
**Зачем:** эксперты назвали прогноз кассового разрыва по выпискам сильным плюсом — он должен
влиять на предложение, а не только на скор. Разрыв (флаг `cash_gap` скоринга или
`cashflow.gap_detected` снимка) не меняет исход, но для APPROVE / COUNTER_OFFER / REJECT:
- `alternative_product_code` — первый из `OVERDRAFT`, `CREDIT_LINE`, который проходит eligibility
  и не совпадает с запрошенным (у ИП Иванова кредитная линия не проходит по сроку работы и
  выручке → `OVERDRAFT`);
- условие в оффере «На период кассового разрыва в ноябре 2026 рекомендуем овердрафт»;
- клиенту: «По выписке ожидается кассовый разрыв в ноябре 2026, для него удобнее овердрафт».

Для ручного решения разрыв остаётся в `rule_trace` — андеррайтер видит его без альтернативы.

### Предодобрение
**Зачем:** на главной кабинета клиент сразу видит «вам доступно до …» — это та же политика, только
по облегчённым данным (оценка скоринга без БКИ и выписок), поэтому осторожнее.
`CreditPolicy.pre_approve(inp, key_rate=…)` по одному продукту:
- стоп-факторы, известные без БКИ (статус по ЕГРЮЛ, грейд E) → предложения нет;
- лимит = min(максимум продукта, k(грейд **на ступень осторожнее**: A→B, B→C, C→D, D — нет) ×
  годовая выручка), вниз до 10 000; выручка неизвестна или лимит ниже минимума продукта → нет;
- `rate_from` — ставка по п. 3 для грейда оценки без залога, с ключевой ставкой и потолком
  господдержки, если компания проходит программу.

В policy_v3 шкала — A–J, ступень осторожнее — следующий грейд (A→B … I→J, J — нет). Лимит не выше и
того, что по этому грейду одобряет автоматика: матрица и максимум на грейд, — клиенту не предлагают
сумму, которую потом не дадут. Ставка — из компонент по PD оценки. Новому клиенту (сегмент
`new_client`, оборотов в банке меньше полугода) предодобрения нет: только полный скоринг по заявке.

В policy_v5 матрицы грейд × сумма нет, автоматика одобряет только в зелёной зоне обеих моделей
(A–D). Оценка для предодобрения знает только PD-модель, поэтому предложение есть, лишь если
осторожный грейд в зоне, где матрица двух моделей может одобрить: на практике оценка A–C. С
оценкой D и хуже предодобрения нет — осторожный грейд уже в жёлтой зоне, заявку проверит человек.

Продукты стартапа (`startup_only` в products) предодобрение по оценке пропускает: выручки у
стартапа нет, предлагать не из чего. Предложение по продукту стартапа даёт только проектная оценка
по бизнес-плану (`basis = project`, раздел
[Проектная оценка](#ветка-стартапа-проектная-оценка-до-заявки)); пересчёт по событиям clients его
не трогает. На главной кабинета стартап видит предскрин, бизнес-план и оценку (bff, блок
`startup`) и только проектное предложение.

**Сверка с ЕГРЮЛ обязательна.** Предскоринг идёт только для компании со статусом `verified`
(снимок clients). Сверки не было (`unverified`) или реестр расходится с кабинетом (`mismatch`) —
предложений нет, прежние снимаются; расхождения — в карточке компании (`verification.discrepancies`).
Сверку decision сам не запускает: у clients это действие клиента
(`POST /organizations/{id}/verification`) или автосверка по выписке ЕГРЮЛ из обогащения заявки.
Итог приходит событием `OrganizationVerified` / `OrganizationVerificationMismatch` и сразу
пересчитывает предложения. В демо все компании сверены, кроме «Вектора» (`mismatch`, S-3) — у него
предодобрения нет.

Предложение действует 30 дней и не пропадает молча: ночной пакет заранее пересчитывает компании,
у которых срок подходит к концу (см. Runtime). Eligibility продукта, срок действия и хранение — в
runtime модуля (#40).

### Обязательные требования закона: `policy_v6`

**Зачем:** закон требует проверить клиента до обслуживания, и не по кредитному риску, а по 115-ФЗ:
перечни Росфинмониторинга, решения МВК о замораживании, ФРОМУ, публичные должностные лица, уровень
риска на платформе «Знай своего клиента» Банка России. ИП — физлицо, и неблагоприятное решение по
нему только автоматически допускается с его согласием (ст. 16 152-ФЗ). Полностью — в
[`compliance-115.md`](../compliance-115.md). v6 = v5 + раздел `compliance` в YAML.

**Вход:** `DecisionInput.aml` — проверка этой заявки из снимка обогащения (источник `aml`):
`ok` с совпадениями, ПДЛ, уровнем ЗСК и бенефициарами; `failed` — не ответили перечни, база ПДЛ,
ЗСК или ЕГРЮЛ, не установить бенефициаров; `not_requested`. `automated_decision_consent` — из
согласий заявки. Прошлые заявки клиента не смотрим: проверка — на каждой.

**Правила:**
1. **Первым, до скоринга** (`aml.lists`, `aml.zsk_stop`): совпадение с перечнем, решением МВК или
   ФРОМУ у компании, учредителя-юрлица цепочки, руководителя, бенефициара или представителя →
   `REJECT`, `STOP_AML_LISTED`, при любом скоре и даже без результата скоринга; уровень ЗСК из
   `compliance.aml.zsk_stop_levels` (высокий) → `REJECT`, `STOP_ZSK_HIGH_RISK`.
2. **Маршрутизация**, вместе с прежней (`route.aml_incomplete`, `route.pep`, `route.zsk`):
   проверка не выполнена → `ROUTE_AML_INCOMPLETE` (спорная); ПДЛ → `ROUTE_PEP` (у иностранного ПДЛ в
   трассе — нужно письменное решение руководителя банка и источник средств); уровень ЗСК из
   `zsk_review_levels` (средний) → `ROUTE_ZSK_MEDIUM_RISK`. Автоматического одобрения нет.
3. **Последним** (`consent.automated_decision`): исход из `automated_decision_consent.outcomes`
   (`REJECT`, `COUNTER_OFFER`) у формы из `legal_forms` (`IE`) без согласия →
   `MANUAL_REVIEW`, первым кодом `ROUTE_AUTOMATED_DECISION_CONSENT`, за ним — причины
   несостоявшегося решения (их видит андеррайтер, клиенту — только текст о согласии, без
   подсказок). Отказ по 115-ФЗ (правило 1) этим правилом не переносится: обслуживать лицо из
   перечня запрещает закон.

Трасса: «совпадений с перечнями нет (перечни на 2026-10-21); бенефициары: Смирнова Анна Сергеевна
— 100.00%», «уровень риска ЗСК: низкий». Клиенту — нейтрально, без перечней, ПДЛ, ЗСК и
бенефициаров: о мерах по 115-ФЗ клиента не информируют.

Golden v6: исходы S-1…S-7 те же, что в v5 (демо-компании чистые), в трассе добавились правила
проверки. `ROUTE_AML_INCOMPLETE` — в `DISPUTE_REASON_CODES`.

### Стоп-факторы до модели: `policy_v7`

**Зачем:** на общей схеме «Стоп-фактор?» стоит сразу после «Запросов», до вызова модели: при
стоп-факторе кредит не дают ни на каких условиях, и считать риск незачем. Раньше стоп-факторы
проверялись внутри решения после скоринга, а при сбое скоринга — не проверялись вовсе: заявка без
результата скоринга сразу уходила андеррайтеру, даже у ликвидированной компании.

- **Отдельный шаг процесса** `check_stop_factors` (маршруты `*_v2`) после обогащения:
  `CreditPolicy.screen` — 115-ФЗ, стоп-факторы ЕГРЮЛ, ФНС, БКИ, Контура, ГИР БО и предскрин
  учредителя, без грейда и без результата скоринга. Сработал — решение принято без модели, процесс
  идёт на шлюз исхода; нет — к скорингу.
- **В самом решении** (`stop_factors.before_scoring: true`) стоп-факторы идут раньше проверки, есть
  ли результат скоринга: без скоринга стоп-фактор всё равно даёт отказ. С результатом скоринга
  трасса та же, что в v6 (golden v7 отличается от v6 только версией).
- Правило ст. 16 152-ФЗ действует и здесь: отказ ИП по стоп-фактору без согласия на
  автоматизированное решение готовит человек.

Из демо стоп-шаг останавливает «Закат» (S-4: ликвидация, просрочки, недоимка) — отказ без
скоринга; остальные компании проходят его к модели.

**«Данные полные?»** (#144, `routing.data_quality: true`): скоринг пометил данные неполными
(`quality = degraded` — не ответили ФНС или БКИ, мало признаков с данными, см.
[scoring](scoring.md#данные-полные--quality_v1)) → `MANUAL_REVIEW` по `ROUTE_SOURCES_FAILED`,
вид — спорная. Правило `route.data_quality` идёт первым в маршрутизации после 115-ФЗ; ставка и
лимиты всё равно посчитаны. На неполных данных и обе модели в красной зоне не дают отказа.
Трасса: «данные неполные: не ответили источники: bki — решает человек». S-6 «Сбой» так и уходит
к андеррайтеру; у остальных демо — «данные полные».

**Две модели и матрица грейд × сумма** (#145): на общей схеме — матрица грейд × сумма, в v5/v6 её
заменили зоны двух моделей, и сумма влияла только через `auto_decision_limit` продукта. В v7 обе
стратегии вместе (`strategy.two_models` и `strategy.risk_matrix` из v4), решает строже из двух:
зоны моделей — можно ли одобрить автоматически, корзина грейда PD-модели — до какой суммы. Выше
автоматики корзины — проверка (`ROUTE_RISK_MATRIX`), выше ручной — отказ (`STOP_RISK_MATRIX`),
если только нет мягких триггеров или сбоя источников. Пример: грейд D, обе модели зелёные,
20 млн — v6 решала сама, v7 отдаёт человеку (автоматика корзины D–E — 15 млн). Предодобрение не
выше автоматики корзины осторожного грейда. В демо матрица добавила причину только «Вектору»
(S-3: грейд F, 10 млн при автоматике корзины F–G до 5 млн); исходы S-1…S-7 те же.

Порядок «ставка → лимит» остаётся: от ставки зависит лимит по платёжеспособности, поэтому на
схеме «как будет» ставка стоит перед расчётом лимита, а не после.

**Полный перечень стоп-факторов** (#146): в v7 есть каждая строка таблицы общей схемы. Новые — в
`stop_factors` (`policy_v7.yaml`):

| Условие | Источник | Ключ YAML | Причина |
|---|---|---|---|
| реорганизация | ЕГРЮЛ, статус `reorganizing` | `registry_statuses` | `STOP_REORGANIZATION` |
| исключение из реестра | ЕГРЮЛ, статус `excluded` | `registry_statuses` | `STOP_EXCLUDED_FROM_REGISTRY` |
| отметка о недостоверности адреса, руководителя или учредителя | ЕГРЮЛ | `unreliable_data` | `STOP_UNRELIABLE_DATA` |
| массовый руководитель | ФНС «Прозрачный бизнес» | `mass_head` | `STOP_MASS_HEAD` |
| срок работы меньше минимума продукта (у `STARTUP` — 0) | ЕГРЮЛ, условия продукта | `business_age` | `STOP_BUSINESS_TOO_YOUNG` |
| компания во внутреннем стоп-листе банка | АБС (порт `BankStopListSource`) | `bank_stop_list` | `STOP_BANK_STOP_LIST` |

**Обороты по счёту в банке** (#151, `limits.bank_turnover: true`): выписки клиента нет — лимит
`by_turnover` (0,5 × поступления за год) и мягкий триггер «разгон оборотов» считаются по оборотам
АБС (`bank_turnover` снимка); в трассе — пометка «(АБС)». Выписка есть — как раньше, по ней. В
демо лимит по оборотам АБС ограничивает только ипотеку «Ромашки» (S-7: 30 млн при лимите
24,25 млн) — она и так у андеррайтера; исходы S-1…S-7 те же.

Источник не ответил — проверка в трассе «не выполнена», заявка уходит на ручную по сбою
источников (стоп-лист — в `_EXTERNAL_SOURCES`). Причина из стоп-листа видна только банку, клиенту —
«по результатам внутренних проверок». Компании для показа — в `external-mocks/README.md`
(`STOP_DEMO`); демо S-1…S-9 этих отметок не имеют, их исходы те же.

### Третьи лица по 115-ФЗ: `policy_v8`

**Зачем:** 115-ФЗ требует идентифицировать не только клиента, представителя и бенефициарного
владельца, но и **выгодоприобретателя** — лицо, к выгоде которого клиент действует (агентский
договор, поручение, комиссия, доверительное управление). Залог третьего лица добавляет ещё одного
участника сделки — залогодателя. Подробно — [compliance-115.md](../compliance-115.md#третьи-лица-выгодоприобретатель-и-залогодатель).

- **Перечни.** Выгодоприобретатель и залогодатель уходят в проверку `aml` (роли `beneficiary`,
  `pledgor`), совпадение — `STOP_AML_LISTED` тем же правилом `aml.listed`, что у остальных
  участников, на шаге стоп-факторов до скоринга; ПДЛ — `ROUTE_PEP`.
- **`route.beneficiary`** (`compliance.third_parties.beneficiary_review: true`): клиент действует к
  выгоде третьего лица → `MANUAL_REVIEW` по `ROUTE_THIRD_PARTY_BENEFICIARY`, вид — проверка.
  Трасса: «клиент действует к выгоде третьего лица: ООО «Принципал» (агентский договор)».
- **`route.third_parties_unknown`** (`require_answers`): нет ответа о выгодоприобретателе или у
  залога третьего лица не указан владелец → `ROUTE_THIRD_PARTIES_UNKNOWN`, вид — спорная. В v8 и
  v9 выключено (форма заявки не спрашивала), трасса пишет «ответа о выгодоприобретателе нет —
  правило выключено, пока форма заявки не спрашивает». **`policy_v10`** включает правило: вопрос
  есть в форме заявки (#209), без ответа решает человек. Golden v10 — входы S-1…S-7 с ответом «в
  своих интересах», исходы те же, что в v9; без ответа — `ROUTE_THIRD_PARTIES_UNKNOWN`.
- Вход — `DecisionInput.third_parties` (`ThirdPartiesInput`): `beneficiary` — `none` / `declared`
  / `not_answered`, `pledgor` — `not_applicable` / `declared` / `unknown`, имена и основание.
  Собирает `input_builder` из `ScoringInputDTO.beneficiary` и залога заявки.

Скоринг (PD- и ML-модель) третьих лиц не читает — меняется только решение. Golden v8: исходы
S-1…S-7 те же, что в v7, в трассе два новых правила.

### Группа риска клиента по 115-ФЗ: `policy_v9`

**Зачем:** ст. 7 п. 1 подп. 3.1 115-ФЗ обязывает банк относить каждого клиента к одной из трёх
групп риска совершения подозрительных операций, подп. 3.2 — снижать выявленный риск; ст. 7 п. 15
запрещает обслуживать того, кто ведёт деятельность без обязательной лицензии. Подробно и таблица
факторов — [compliance-115.md](../compliance-115.md#группа-риска-клиента).

- **`aml.license`** (`compliance.licensing.licensed_okved`): основной ОКВЭД начинается с
  лицензируемого префикса, а действующей лицензии с этим префиксом в реестре нет →
  `STOP_UNLICENSED_ACTIVITY`, отказ вместе с правилами 115-ФЗ, до скоринга (и на шаге
  `check_stop_factors`). Снимок без реестра лицензий (до v9) — правило только в трассе.
- **`aml.risk_group`** (`compliance.aml_risk`): группа по факторам — перечни, ЗСК, ПДЛ, участники из
  государств `high_risk_countries`, иностранные участники, расхождение названных клиентом
  бенефициаров с ЕГРЮЛ, выгодоприобретатель, ОКВЭД из `high_risk_okved`. Считается вместе с
  остальными правилами 115-ФЗ, поэтому есть в трассе любого решения с выполненной проверкой.
  Трасса: «группа риска по 115-ФЗ: высокая — учредитель Хоссейни Али Реза — IR, государство не
  выполняет рекомендации ФАТФ».
- **`route.aml_high_risk`** (`high_group_review: true`): высокая группа → `MANUAL_REVIEW` по
  `ROUTE_AML_HIGH_RISK`, вид — проверка; в трассе — какие меры по снижению риска нужны.
- Вход — новые поля `AmlInput`: `foreign_participants` (кто и страна), `owners_declared`,
  `owner_discrepancies`, `licensed_okved`. Собирает `input_builder` из снимка `aml`.

Кредитный грейд и модели не меняются. Golden v9: исходы S-1…S-7 те же, что в v8, в трассе два
новых правила — у демо низкая группа, лицензия не нужна.

## Тексты для клиента

`explanations_ru.yaml`: вводная фраза исхода + тексты причин + подсказки (`improvement_hints`, к
ним добавляются подсказки факторов скоринга). Принципы: никаких внутренних цифр модели, порогов и
названий правил; говорим **что** и **что можно сделать**; при стоп-факторе — нейтрально, без
деталей кредитной истории. Подстановки — только суммы оффера, срок, месяц разрыва, название
продукта и вид залога; загрузчик проверяет это при старте.

Граница раскрытия: `DecisionFacade.get_decision` (банк) отдаёт `reason_codes`, `rule_trace`,
лимиты и ключевую ставку; `get_client_view` (клиент) — только исход, условия, объяснение,
подсказки и дозапрос: у `ClientDecisionDTO` этих полей нет совсем.

## Runtime: команды, события, API

**Консьюмер `decision.commands`** (group `decision.commands`):
- `CheckStopFactors` (policy_v7, шаг процесса `check_stop_factors` до скоринга) →
  `DecisionInputBuilder.collect` → `CreditPolicy.screen` без результата скоринга. Ни один
  стоп-фактор не сработал → `StopFactorsPassed {application_id}`, ничего не пишется. Сработал →
  запись в `decision_results` как у авторешения (без ссылки на скоринг) и обычный `DecisionMade`
  (REJECT; у ИП без согласия на авторешение — MANUAL_REVIEW). Повтор команды — то же решение.
- `MakeDecision` → `DecisionInputBuilder.collect` → `CreditPolicy.decide` → платёж оффера через
  `products.calculate_payment` (одна формула на систему) → запись в `decision_results` → outbox
  `DecisionMade {decision_id, outcome, offer?, decided_by, requested_info?, client_explanation,
  improvement_hints, alternative_product_code}`, `causation_id` = event_id команды. Оффер есть
  только у APPROVE (`as_requested`) и COUNTER_OFFER (`counter`), действует 7 дней. Повтор команды
  с тем же event_id — то же решение и тот же ответ, новой записи нет.
- `RecordManualDecision` — проверки андеррайтера: комментарий обязателен; APPROVE и COUNTER_OFFER —
  с условиями, REQUEST_INFO — с документами или полями, MANUAL_REVIEW вручную нельзя; сумма, срок и
  ставка — в рамках продукта из заявки; сумма ≤ полномочий `underwriter` 50 млн (выше — кредитный
  комитет). Нарушение → `ManualDecisionRejected {application_id, task_id, reason}`, решение не
  пишется; process открывает андеррайтеру новую задачу, `reason` — в её поле `reason`. Успех → новая запись `decided_by=underwriter`, `override_of` = последнее авторешение
  (оно остаётся для аудита), проверки — в `rule_trace`, комментарий клиенту не уходит.

**Консьюмер `clients.events`** (group `decision.clients-events`): `FinancialReportSubmitted`,
`OrganizationVerified` и `OrganizationVerificationMismatch` (сверка с реестром могла сменить статус
или найти расхождение) → пересчёт предодобрений: компания не `verified` — предложений нет, иначе
по каждому активному продукту eligibility products (не проходит — пропуск) → `scoring.estimate` без
БКИ и выписок → `CreditPolicy.pre_approve` → предложения на 30 дней, пересчёт перезаписывает все
предложения компании (и снимает их) → `PreApprovedOffersUpdated {organization_id}`. Сид
`backend/seed/decision.py` считает их для всех демо-компаний тем же use case, без события (сид идёт
на каждом старте).

**Ночной пакет** (`jobs.py` → `RefreshExpiringPreApprovedUseCase`, запускается в
`module.startup` при `RUN_BACKGROUND_JOBS`): раз в `DECISION_PRE_APPROVAL_REFRESH_INTERVAL_SECONDS`
(по умолчанию сутки) берёт компании, у которых хоть одно предложение истекает в ближайшие
`DECISION_PRE_APPROVAL_REFRESH_DAYS` дней (по умолчанию 3; уже истекшие — тоже), и пересчитывает
каждую в своей транзакции тем же use case — со сверкой и `PreApprovedOffersUpdated` (без
`causation_id`). Ошибка одной компании не останавливает остальные: она попадёт в следующий проход.
Первый проход — через `DECISION_PRE_APPROVAL_REFRESH_FIRST_RUN_SECONDS` (60) после старта, чтобы не
пересекаться с сидом. События clients по-прежнему пересчитывают сразу.

**API** `GET /organizations/{id}/pre-approved-offers` — `organizations.read`; клиент видит только
свои компании (`clients.ensure_can(view)`, чужая — 404), сотрудник банка — любые. Действующие
предложения, крупные первыми, с оговоркой «предварительно, окончательное решение — после проверки».

**API предскрина учредителя** (ветка стартапа):

| Метод | Путь | Доступ | Что |
|---|---|---|---|
| POST | `/organizations/{id}/founder-prescreen` | `organizations.read`; клиенту — право подавать заявки от компании (`submit_application`), сотруднику банка — любая | запустить предскрин → 201; 422 `founder_not_found` / `consent_required`; 503 — БКИ не ответило |
| GET | `/organizations/{id}/founder-prescreen` | как у предодобрений | последний предскрин; 404 — ещё не было |

Ответ: `{status: passed | failed, founder: {account_id, name}, checked_at, valid_until, valid,
reasons: [{code, passed, message}]}`; `valid: false` — истёк, для заявки на `STARTUP` нужен новый.
Тот же предскрин bff берёт через `DecisionFacade.get_founder_prescreen`.

**API проектной оценки** (ветка стартапа, #156):

| Метод | Путь | Доступ | Что |
|---|---|---|---|
| POST | `/organizations/{id}/project-assessment` | как у предскрина: клиенту — `submit_application` в компании | оценить проект по бизнес-плану из кабинета → 201; 422 `business_plan_required` / `product_not_eligible` |
| GET | `/organizations/{id}/project-assessment` | как у предодобрений | последняя оценка; 404 — ещё не было |

Ответ: `{status: passed | failed, product_code, max_amount, plan_revision, checked_at, valid_until,
valid, reasons: [{code, passed, message}]}`. `passed` — предложение `product_code` до `max_amount`,
оно же в `pre-approved-offers` с `basis: "project"`. Цифр модели в ответе клиенту нет — по ним
угадываются пороги; андеррайтер видит их в карточке (`DecisionFacade.get_project_assessment`,
`figures`).

**Таблицы:** `decision_results` (решение неизменяемо; `sequence` — номер решения внутри заявки,
последнее = наибольший, даже при одинаковом времени; `requested_by_command` уникален —
идемпотентность; `triggers` и `rate_breakdown` — с `decision_0002`, расширенные лимиты — в JSON
`limits`), `decision_pre_approved_offers` (PK `organization_id, product_code`),
`decision_founder_prescreens` (с `decision_0003`: строка на каждую проверку, индекс
`organization_id, checked_at`, действует последняя), `decision_project_assessments` (с
`decision_0004`: строка на каждую оценку, причины и цифры — JSON, индекс `organization_id,
checked_at`, действует последняя). У предложений `basis`: `estimate` — по оценке без заявки,
`project` — по проектной оценке.

Андеррайтер видит всё это в `GET /bff/backoffice/applications/{id}`: `scoring.segment`,
`scoring.pd_12m`, `scoring.reason_codes`, `scoring.ml` (оценка ML-модели), `decision.triggers`,
`decision.rate_breakdown`, `decision.limits.binding`, `decision.review` (`check` / `dispute` у
`MANUAL_REVIEW`). В очереди `GET /bff/backoffice/queue` у задачи — `review` того же смысла.

Тесты — `tests/decision/runtime/`: оба консьюмера через настоящие подписки и inbox, идемпотентность,
отказы ручного решения (без комментария, вне продукта, сверх полномочий), цепочка `override_of`,
права API, предодобрение пропускает неподходящие продукты, без сверки и при расхождении с реестром
предложений нет, клиентский DTO без внутренних данных, сид на настоящих clients, products и
scoring. Ночной пакет: продлевает истекающие и истекшие, свежие не трогает, ошибка одной компании
не мешает другим; цикл и его запуск с приложением — `test_decision_runtime_jobs.py`. Предскрин —
`test_decision_runtime_prescreen.py`: срок 30 дней, причины отказа сохраняются, действует
последний, без согласия в БКИ не ходим, нет учредителя по реестру, БКИ не ответило — 503 и ничего
не сохранено. Проектная оценка — `test_decision_runtime_project.py`: предложение на 30 дней вниз
до шага, платёж по верхней ставке коридора, срок в рамках продукта, без предскрина scoring это
знает, непройденная снимает предложение, меньше минимума продукта — нечего предложить (настоящий
scoring), предложения по оценке и проектные не трут друг друга, без бизнес-плана и компании с
оборотами — 422. Сквозной путь стартапа — S-9 (без проектной оценки) и S-10 (бизнес-план →
«предодобрено до N» → заявка → андеррайтер → оффер) в `tests/scenarios`.

## Моки

Своих моков у decision **нет**: внешние данные приходят через `enrichment` (ЕГРЮЛ, ФНС, БКИ,
ГИР БО, Контур, БКИ руководителя, БКИ учредителя для предскрина — external-mocks за адаптерами),
выписки — синтетика `seed/statements`. Ключевая ставка `KEY_RATE` — значение из настроек
(по умолчанию 14,00%), не запрос к ЦБ.

## Упрощения

- Действует одна версия политики (`policy_v4`), выбор версии на заявку и сравнение версий на
  одной заявке — Could.
- Учредитель стартапа — руководитель по реестру: долей участников в данных нет, предскрин
  проверяет одного человека.
- Пороги матрицы, лимитов и компоненты ставки — стартовые синтетические, подобраны так, чтобы исходы
  демо S-1…S-8 не изменились.
- Залог оценивается по заявленной стоимости (оценка в моках — Could).
- Повторная проверка обязательных документов продукта (`INFO_MISSING_DOCUMENT`) не делается:
  комплектность проверяет applications при подаче.
