# Модуль `decision`

## Зачем

Отвечает на вопрос **«что банк готов предложить этому заёмщику по этому продукту»**. ТЗ различает
оценку риска и кредитное решение: риск даёт `scoring` (скор, грейд, флаги), а decision добавляет
продукт, сумму и срок, внешние проверки и правила банка — **одинаковый риск даёт разные условия на
разных продуктах**. Итог не бинарный: одобрить как просили, предложить другие условия, запросить
информацию, отдать андеррайтеру или отказать — с альтернативным продуктом.

Эксперты вебинара 21.10 просили, чтобы **банк понимал, почему предложено именно это**: каждое
проверенное правило попадает в `rule_trace` с цифрами, лимиты видны по отдельности, ставка — по
шагам. Клиент видит только итог и человеческое объяснение без внутренних цифр.

**Не отвечает за:** оценку риска (берёт готовый скор), статусы заявки (process, applications),
очередь андеррайтера (process).

## Язык модуля

| Термин | Значение |
|---|---|
| Кредитная политика (`CreditPolicy`) | версионированный набор правил банка: действует `policy_v4`, `policy_v1`–`policy_v3` — для истории и отката |
| Стоп-фактор | условие, при котором отказ без вариантов |
| Мягкий триггер | не отказ, а повод показать заявку андеррайтеру (policy_v3) |
| Матрица грейд × сумма | по корзине грейдов: до какой суммы решает автоматика, до какой — человек, выше — отказ (policy_v3) |
| Лимит | наибольшая сумма, которую банк готов дать: минимум из ограничений (в policy_v3 — семи, с `binding`) |
| LTV | доля стоимости залога, под которую банк даёт деньги |
| Платёжеспособность | платёж ≤ 40% свободного денежного потока |
| Маршрутизация | правила «решать автоматически или отдать андеррайтеру» |
| Трасса правил (`rule_trace`) | что проверено, сработало ли и почему — для аудита и андеррайтера |
| Причина (`ReasonCode`) | внутренний код решения; у каждого — текст для клиента |
| Предскрин учредителя (`FounderPrescreen`) | проверка личной кредитной истории учредителя стартапа до заявки: `passed` / `failed`, действует 30 дней (policy_v4) |

## Устройство

- `domain/` — чистый Python: вход политики (`DecisionInput`), `CreditPolicy.decide(inp, key_rate=…)`
  без IO и без `now()`, итог `PolicyDecision`, запись решения `DecisionResult`.
- `application/input_builder.py` — собирает `DecisionInput` из фасадов соседей: заявка и копия
  условий продукта (`applications.get_scoring_input`), дозапросы (`applications.get_card`),
  ЕГРЮЛ/ФНС/БКИ, ГИР БО, Контур, БКИ руководителя и прогноз по выписке
  (`enrichment.get_snapshot`), грейд, PD и флаги
  (`scoring.get_result`), программа господдержки и eligibility альтернатив (`products`), для
  продукта стартапа — предскрин учредителя на дату подачи (своё хранилище). Грейд
  скоринга переводится на шкалу политики (`on_scale`): результат scorecard_v1 (A–E) для policy_v3
  — A→B, B→D, C→F, D→H, E→J, результат PD-модели (A–J) для policy_v1/v2 — попарно в A–E.
- `application/founder_prescreen.py` — предскрин учредителя стартапа (раздел
  [Ветка стартапа](#ветка-стартапа-policy_v4-и-предскрин-учредителя)).
- `infrastructure/config/policy_v4.yaml` (действующая), `policy_v1.yaml`–`policy_v3.yaml` — пороги и
  коэффициенты, `explanations_ru.yaml` — тексты
  для клиента. Оба файла проверяются Pydantic-схемой при старте (`config_loader.py`): нет грейда,
  кода причины, текста или в шаблоне неизвестная подстановка → `PolicyConfigError`, приложение не
  стартует. Логика правил — в коде, цифры — в YAML: калибровка меняется без правки кода.
- `config.py` — `DECISION_KEY_RATE`.

Действующая версия — `_DEFAULT_POLICY` в `config_loader.py`; она же пишется в журнал решения
(`decision_results.policy_version`) и видна андеррайтеру. Вышедшая версия не правится: следующая

файлах прежних версий этих ключей нет, поэтому их решения и трасса не изменились (golden v1 и v2
считаются на scorecard_v1, как в момент выхода).

## Правила `policy_v1` по порядку

Первое терминальное правило останавливает конвейер; всё проверенное — в `rule_trace`.

### 1. Стоп-факторы → `REJECT`
**Зачем:** есть ситуации, в которых кредит не выдают ни на каких условиях — нет смысла считать лимит.

| Условие | Причина |
|---|---|
| статус по ЕГРЮЛ `liquidating` / `liquidated` | `STOP_LIQUIDATION` |
| статус `bankrupt` | `STOP_BANKRUPTCY` |
| руководитель дисквалифицирован (ФНС) | `STOP_DISQUALIFIED_HEAD` |
| просрочка (текущая или за 12 мес.) **> 90** дней (БКИ) | `STOP_OVERDUE_90` |
| грейд **E** | `STOP_GRADE_E` |

Записываются все сработавшие стоп-факторы, альтернатива не предлагается.

### `policy_v2`: стоп-факторы новых источников

Из таблицы стоп-факторов общей схемы — там, где у нас есть данные. Пороги стартовые, все в
`policy_v2.yaml`. Источник не ответил или не запрошен → проверка в трассе «не выполнена», а
решение уходит на ручную проверку по `ROUTE_SOURCES_FAILED` (сбой) либо идёт дальше (нет согласия
руководителя).

| Условие | Источник | Ключ YAML | Причина |
|---|---|---|---|
| текущая просрочка компании **≥ 30** дней | БКИ | `current_overdue_days: 30` | `STOP_CURRENT_OVERDUE` |
| текущая просрочка руководителя **≥ 30** дней | БКИ руководителя (с его согласия) | `current_overdue_days: 30` | `STOP_HEAD_OVERDUE` |
| есть решения о приостановлении операций по счетам | ФНС | `account_blocks: true` | `STOP_ACCOUNT_BLOCKS` |
| недоимка **> 300 000 ₽** | ФНС | `tax_arrears_above` | `STOP_TAX_ARREARS` |
| есть сообщения о банкротстве | Контур | `bankruptcy_messages: true` | `STOP_BANKRUPTCY_MESSAGE` |
| исполнительные производства **> 10%** годовой выручки | Контур | `enforcement_revenue_share` | `STOP_LARGE_ENFORCEMENT` |
| иски к компании **> 20%** годовой выручки | Контур | `lawsuits_revenue_share` | `STOP_LARGE_LAWSUITS` |
| отрицательный собственный капитал в последнем периоде | ГИР БО | `negative_equity: true` | `STOP_NEGATIVE_EQUITY` |
| адрес массовой регистрации (в v1 — ручная проверка) | ЕГРЮЛ | `mass_address: true` | `STOP_MASS_ADDRESS` |
| основной ОКВЭД из стоп-листа банка (класс `92` — азартные игры) | ЕГРЮЛ | `okved_classes` | `STOP_FORBIDDEN_OKVED` |

Годовая выручка для долевых порогов — последний период ГИР БО, иначе ФНС, иначе отчёт клиента.

Маршрут v2: недоимка больше нуля, но не выше стоп-порога → `ROUTE_TAX_ARREARS` (`routing.tax_arrears`).
Выручка ГИР БО ниже заявленной по-прежнему ловится флагом `revenue_mismatch` через дозапрос выписки.

Чего из таблицы схемы нет — данных нет: реорганизация и исключение из реестра, недостоверность адреса
или руководителя, массовый руководитель, экстремисты, стоп-лист банка и 115-ФЗ. Возраст бизнеса
проверяет eligibility продукта при подаче.

### `policy_v3`: стратегия решения

«Стратегия решения» общей схемы на шкале A–J PD-модели (`scoring`, `pd_model_v2`). Стоп-факторы и
дозапрос — как в v2; грейд больше не стоп-фактор и не маршрут (`stop_factors.grades: []`,
`routing.grades: []`) — его отсекает матрица. Всё — в `policy_v3.yaml`.

**Порядок после стоп-факторов и дозапроса:**
1. ставка из компонент и лимиты — считаются всегда, андеррайтер видит их и в ручном решении;
2. маршруты v2 (сумма выше автоматики продукта, расхождения, сбой источников, массовый адрес);
3. мягкие триггеры → `ROUTE_SOFT_TRIGGER`, список — в `decision.triggers: [{code, detail}]`;
4. матрица грейд × сумма → одобрить (дальше лимиты) / `ROUTE_RISK_MATRIX` / `STOP_RISK_MATRIX`.
   Сбой источников и мягкие триггеры идут **раньше** матрицы: при них решает человек, а не отказ;
5. исход — как в v1: в пределах лимита — APPROVE, иначе COUNTER_OFFER (сначала удлиняем срок в
   рамках продукта, потом снижаем сумму), ниже минимума продукта — REJECT.

**Мягкие триггеры** (`strategy.soft_triggers`):

| Триггер | Условие | Источник |
|---|---|---|
| `tax_arrears` | недоимка больше нуля, но не выше стоп-порога 300 000 ₽ (в v2 это был `ROUTE_TAX_ARREARS`) | ФНС |
| `head_change` | руководитель сменился меньше **6** мес. назад (запись в ЕГРЮЛ позже регистрации) | ЕГРЮЛ, `head_since` |
| `turnover_spike` | поступления за последние **3** мес. выписки в среднем больше **1,5 ×** среднего за прежние месяцы | выписка |

Нет данных (ФНС не ответила, ЕГРЮЛ не сообщил дату, выписки нет) — триггер в трассе «не
выполнен». Смену руководителя Контур в наших данных не отдаёт — смотрим ЕГРЮЛ.

**Матрица грейд × сумма** (`strategy.risk_matrix`):

| Корзина | Автоматика до | Ручная до | Выше |
|---|---|---|---|
| A–C | 50 млн | без ограничения | — |
| D–E | 15 млн | 50 млн | отказ |
| F–G | 5 млн | 20 млн | отказ |
| H–J | — | 3 млн | отказ |

**Лимит** — минимум из ограничений, `limits.binding` — какое дало минимум:

| Ограничение | Как | Причина |
|---|---|---|
| `by_product` | максимум продукта | `LIMIT_BY_PRODUCT` |
| `by_revenue` | k(грейд) × годовая выручка: A 0,5 · B 0,45 · C 0,4 · D 0,3 · E 0,25 · F 0,2 · G 0,15 · H 0,1 · I 0,05 · J 0 | `LIMIT_BY_REVENUE` |
| `by_turnover` | 0,5 × обороты по счёту за год по выписке; выписки нет — не ограничиваем | `LIMIT_BY_TURNOVER` |
| `by_capacity` | платёж ≤ 40% свободного потока, как в v1 | `LIMIT_BY_PAYMENT_CAPACITY` |
| `by_grade` | максимум на грейд: A 60 · B 50 · C 40 · D 30 · E 20 · F 10 · G 5 · H 2 · I 1 · J 0 млн | `LIMIT_BY_GRADE` |
| `by_group` | 100 млн − остаток долга по действующим кредитам (БКИ). Связанных компаний в данных нет — группа это сама компания | `LIMIT_BY_GROUP` |
| `by_ltv` | для залоговых — как в v1 | `LIMIT_BY_LTV` |

**Ставка** = фондирование + ожидаемые потери + капитал + маржа, в коридоре продукта, потолок
господдержки — как в v1:
- фондирование = ключевая + спред 1,0 п.п.;
- ожидаемые потери = PD × LGD × 100: LGD 0,45 без залога, 0,25 при покрытии залогом ≥ 1;
- капитал 2,0 п.п., маржа 3,5 п.п.;
- у результата scorecard_v1 PD нет — берём осторожную 10% (`pd_if_unknown`).

Разбивка — в `decision.rate_breakdown: {funding, expected_loss, capital, margin, total}`, `total` —
итог после коридора.

**Обеспечение:** поручительство собственника в `offer.conditions` для грейдов F–G и сумм больше
20 млн (`strategy.guarantee`), если у продукта своего поручительства нет.

### Ветка стартапа: `policy_v4` и предскрин учредителя

**Зачем:** у компании младше полугода или без годовой отчётности нет ни оборотов, ни выручки —
скоринг и лимиты по ним о проекте ничего не скажут. Ветка «нет бизнеса» общей схемы: личный
скоринг учредителя (предскрин) → прошёл → проектная оценка андеррайтером; не прошёл — «отказ
(стартап)». v4 = v3 + ключ `startup` в YAML; для остальных продуктов решения и трасса как в v3.

**Предскрин** — до заявки, по кнопке в кабинете (`FounderPrescreenUseCase`,
`application/founder_prescreen.py`):
1. учредитель — участник компании, чьё ФИО совпало с руководителем по реестру
   (`clients.get_registry_head`); такого нет → 422 `founder_not_found`;
2. нужно его действующее согласие `credit_bureau_personal` (`identity`); нет → 422
   `consent_required`, в БКИ не ходим;
3. запрос в БКИ физлица сразу, без заявки и без кеша (`enrichment.lookup_person_bureau`), оценка —
   `scoring.prescreen_person`: правила `prescreen_v1`, см.
   [scoring](scoring.md#предскрин-учредителя-prescreen_v1). Бюро не ответило → 503, ничего не
   сохраняется;
4. результат — новая запись, действует последняя; срок — 30 дней (`PRESCREEN_VALID_DAYS`), как у
   предодобрения. `failed` — это «отказ (стартап)»: клиент видит причины (`reasons[].message`) без
   порогов.

**Правила v4** (`startup.products: [STARTUP]`):
- стоп-фактор `stop.founder_prescreen`: заявка на продукт стартапа без пройденного предскрина,
  действовавшего на дату подачи (`submitted_at`) → REJECT `STOP_FOUNDER_PRESCREEN`, альтернативы
  нет. Статус собирает `input_builder` по последнему предскрину компании:

  | `founder_prescreen` | Когда | Итог |
  |---|---|---|
  | `passed` | пройден и действовал при подаче | дальше по правилам |
  | `failed` | не пройден | `STOP_FOUNDER_PRESCREEN` |
  | `expired` | истёк к подаче | `STOP_FOUNDER_PRESCREEN` |
  | `missing` | предскрина не было | `STOP_FOUNDER_PRESCREEN` |

  Клиенту: «Для кредита на запуск бизнеса нужна действующая проверка личной кредитной истории
  учредителя», подсказка — пройти проверку в кабинете и подать заявку снова;
- матрица грейд × сумма для продукта стартапа не применяется — в трассе `strategy.risk_matrix`
  «вместо матрицы — проектная оценка андеррайтером». Грейд стартапа считается по карте
  `new_client` без оборотов и о проекте ничего не говорит;
- `auto_decision_limit` у `STARTUP` — 0, поэтому с пройденным предскрином заявка всегда уходит на
  `MANUAL_REVIEW` (`ROUTE_AMOUNT_OVER_AUTO_LIMIT`). Маршрут `startup_v1` даёт андеррайтеру форму
  `project_assessment`: бизнес-план, финмодель, обеспечение, господдержка. Клиент видит этап
  «Проектная оценка». Ставка и лимиты посчитаны как в v3 — андеррайтер видит их рядом с проектом.

Остальные стоп-факторы v2 — статус по ЕГРЮЛ, просрочки, ФНС, Контур — для стартапа действуют как
обычно.

### Две модели: `policy_v5`

**Зачем:** скоринг считает на каждой заявке две оценки риска — экспертную PD-модель и обученную
ML-модель ([scoring](scoring.md#ml-модель-ml_logreg_v1)), обе на шкале A–J. Где модели согласны,
решает автоматика; где расходятся или видят умеренный риск, решает андеррайтер — и видит обе
оценки. v5 = v4, в YAML вместо `strategy.risk_matrix` — `strategy.two_models`.

**Зоны** по грейду, одинаковые для обеих моделей: green A–D (PD < 2,75%), yellow E–G (2,75–9%),
red H–J (от 9%). **Матрица** (строка — PD-модель, столбец — ML-модель):

| PD ↓ / ML → | green | yellow | red |
|---|---|---|---|
| **green** | одобрение | проверка | спорная |
| **yellow** | проверка | проверка | спорная |
| **red** | спорная | спорная | отказ |

- **одобрение** — дальше лимиты как прежде: APPROVE или COUNTER_OFFER;
- **проверка** (`ROUTE_MODELS_CHECK`) — `MANUAL_REVIEW`, вид `check`;
- **спорная** (`ROUTE_MODELS_DISAGREE`) — `MANUAL_REVIEW`, вид `dispute`;
- **отказ** (`STOP_MODELS_HIGH_RISK`) — REJECT. Исключение: данные неполные (сбой источников) —
  модели посчитаны не на всём, решает человек (`dispute` по `ROUTE_SOURCES_FAILED`);
- оценки ML нет (результат до `scoring_0003`) — `ROUTE_ML_UNAVAILABLE`, `dispute`.

**Поверх матрицы**, в прежнем порядке правил:
1. стоп-факторы → REJECT при любых моделях;
2. выручка не подтверждена, дозапроса ещё не было → REQUEST_INFO;
3. расхождения в данных — верификация, выручка после дозапроса, сбой источников — делают заявку
   спорной;
4. мягкие триггеры и сумма выше `auto_decision_limit` продукта — не меньше проверки.

Мягкие триггеры не спасают от отказа, если обе модели в красной зоне. Для продукта стартапа матрица
не применяется, как в v4 (проектная оценка).

**Вид ручной проверки** — `review_kind` в контракте (`decision/facade.py`): `dispute`, если среди
причин есть `ROUTE_MODELS_DISAGREE`, `ROUTE_ML_UNAVAILABLE`, `ROUTE_SOURCES_FAILED`,
`ROUTE_VERIFICATION_MISMATCH`, `ROUTE_MASS_ADDRESS` или `ROUTE_REVENUE_MISMATCH`, иначе `check`.
Вид выводится из кодов причин, поэтому миграции не нужно, и он есть у решений любой версии.

Трасса: правило `strategy.two_models`, например «PD-модель: грейд A (PD 0.41%) — зелёная;
ML-модель: грейд C (PD 1.39%) — зелёная → одобрение, дальше лимиты». Клиент про модели не узнаёт:
тексты причин общие («Специалист банка посмотрит заявку перед решением»).

### 2. Дозапрос → `REQUEST_INFO`
**Зачем:** расхождение выручки с ФНС не повод отказывать — повод попросить подтверждение.
Флаг скоринга `revenue_mismatch`, а закрытого дозапроса с `bank_statement` ещё не было (видно по
`applications.get_card().info_requests`, статус не `open`) → запросить выписку: «Подтвердите
выручку выпиской по счёту за 6 месяцев». Дозапрос уже был и выписка выручку не подтвердила —
идём дальше, маршрутизация отдаст заявку андеррайтеру.

### 3. Ставка
**Зачем:** эксперты просили учитывать «текущую ситуацию в кредитовании» — ключевая ставка ЦБ
сдвигает цену денег для банка.

```
rate = clamp(rate_base + premium(грейд) − discount(залог) + (key_rate − key_rate_reference),
             rate_base, rate_max)
GOV_SUPPORT: rate = min(rate, support_program.rate_cap), если компания в реестре МСП
             и её класс ОКВЭД — в списке программы
```

| Параметр | Значение |
|---|---|
| надбавка за грейд | A 0 · B +1,5 · C +3,5 · D +6,0 п.п. |
| скидка за залог | −1,5 п.п. при покрытии (стоимость залога / сумма) ≥ 1 |
| `key_rate_reference` | 16,50% — ставка, под которую откалиброван каталог продуктов |
| `DECISION_KEY_RATE` | env, по умолчанию 16,50% (синтетика, совпадает с опорной: каталог не сдвигается). **На дату сдачи сверить с cbr.ru** |

Ставка считается до лимита: от неё зависит платёжеспособность.

### 4. Лимит
**Зачем:** сумма ограничена тем, сколько бизнес реально может обслуживать, а не только продуктом.

```
limit = min(
    product.amount_max,                                   # LIMIT_BY_PRODUCT
    k(грейд) × годовая выручка,                            # LIMIT_BY_REVENUE
    LTV(тип залога) × стоимость залога,                    # LIMIT_BY_LTV — только залоговые продукты
    сумма, при которой платёж ≤ 40% свободного потока,     # LIMIT_BY_PAYMENT_CAPACITY
)
```

| Параметр | Значение |
|---|---|
| k(грейд) | A 0,5 · B 0,4 · C 0,25 · D 0,15 |
| выручка для k | меньшая из заявленной (последний годовой отчёт) и по ФНС — консервативно |
| LTV | недвижимость 0,7 · транспорт 0,6 · оборудование 0,5 · товары 0,3 |
| свободный поток | **по выписке, если она есть**: средний месячный чистый поток − платежи по кредитам из БКИ; иначе по отчёту: (выручка − расходы) / 12 − платежи по БКИ |
| нет расходов в отчёте | принимаем 80% выручки — допущение пишется в `rule_trace` |
| платёж | аннуитет, та же формула, что `products.calculate_payment` |

Банк видит все четыре лимита отдельно (`limits.by_revenue`, `by_ltv`, `by_capacity` при запрошенном
сроке) — понятно, какое ограничение сработало.

### 5. Маршрутизация → `MANUAL_REVIEW`
**Зачем:** автоматика решает только то, в чём уверена; остальное — андеррайтеру с готовой трассой.

| Условие | Причина |
|---|---|
| сумма > `auto_decision_limit` продукта (у `MORTGAGE` — 0, т.е. всегда) | `ROUTE_AMOUNT_OVER_AUTO_LIMIT` |
| грейд **D** | `ROUTE_GRADE_D` |
| флаг `verification_mismatch` (или статус верификации `mismatch`) | `ROUTE_VERIFICATION_MISMATCH` |
| флаг `revenue_mismatch` после дозапроса выписки | `ROUTE_REVENUE_MISMATCH` |
| флаг `bureau_unavailable` или не ответил внешний источник (ЕГРЮЛ, ФНС, БКИ; в v2 — и ГИР БО, Контур, БКИ руководителя); нет результата скоринга | `ROUTE_SOURCES_FAILED` |
| флаг `mass_address` | `ROUTE_MASS_ADDRESS` |

`thin_file` **не маршрутизирует** (только −10 баллов в скоринге) — иначе молодой ИП (S-2) никогда
не получит встречное предложение. Ставка и лимиты для ручного решения всё равно посчитаны.

### 6. Исход
- запрошенная сумма в пределах лимита, срок в рамках продукта, платёж проходит → **APPROVE** как
  просили;
- иначе **COUNTER_OFFER**: сумма = меньшее из запрошенной и лимитов, округлённое **вниз до
  10 000**; срок — кратчайший от запрошенного в рамках продукта, при котором платёж проходит
  платёжеспособность (если не проходит и на максимальном сроке — сумма по платёжеспособности на
  максимальном сроке). Клиенту объясняем ограничение, которое определило сумму;
- сумма ниже минимума продукта → **REJECT** (`LIMIT_BELOW_PRODUCT_MIN`) с альтернативой: есть
  залог, а продукт беззалоговый → `SECURED`; ожидается кассовый разрыв → продукт под него;
  иначе `OVERDRAFT`, если лимит дотягивает до его минимума.

Оффер: схема погашения — первая из продукта, условия (залог, поручительство, целевое
использование, кассовый разрыв), платёж считает `products.calculate_payment`, срок действия 7 дней.

### Кассовый разрыв в решении
**Зачем:** эксперты назвали прогноз кассового разрыва по выпискам сильным плюсом — он должен
влиять на предложение, а не только на скор. Разрыв (флаг `cash_gap` скоринга или
`cashflow.gap_detected` снимка) не меняет исход, но для APPROVE / COUNTER_OFFER / REJECT:
- `alternative_product_code` — первый из `OVERDRAFT`, `CREDIT_LINE`, который проходит eligibility
  и не совпадает с запрошенным (у ИП Иванова кредитная линия не проходит по сроку работы и
  выручке → `OVERDRAFT`);
- условие в оффере «На период кассового разрыва в ноябре 2026 рекомендуем овердрафт»;
- клиенту: «По выписке ожидается кассовый разрыв в ноябре 2026, для него удобнее овердрафт».

Для ручного решения разрыв остаётся в `rule_trace` — андеррайтер видит его без альтернативы.

### Предодобрение
**Зачем:** на главной кабинета клиент сразу видит «вам доступно до …» — это та же политика, только
по облегчённым данным (оценка скоринга без БКИ и выписок), поэтому осторожнее.
`CreditPolicy.pre_approve(inp, key_rate=…)` по одному продукту:
- стоп-факторы, известные без БКИ (статус по ЕГРЮЛ, грейд E) → предложения нет;
- лимит = min(максимум продукта, k(грейд **на ступень осторожнее**: A→B, B→C, C→D, D — нет) ×
  годовая выручка), вниз до 10 000; выручка неизвестна или лимит ниже минимума продукта → нет;
- `rate_from` — ставка по п. 3 для грейда оценки без залога, с ключевой ставкой и потолком
  господдержки, если компания проходит программу.

В policy_v3 шкала — A–J, ступень осторожнее — следующий грейд (A→B … I→J, J — нет). Лимит не выше и
того, что по этому грейду одобряет автоматика: матрица и максимум на грейд, — клиенту не предлагают
сумму, которую потом не дадут. Ставка — из компонент по PD оценки. Новому клиенту (сегмент
`new_client`, оборотов в банке меньше полугода) предодобрения нет: только полный скоринг по заявке.

В policy_v5 матрицы грейд × сумма нет, автоматика одобряет только в зелёной зоне обеих моделей
(A–D). Оценка для предодобрения знает только PD-модель, поэтому предложение есть, лишь если
осторожный грейд в зоне, где матрица двух моделей может одобрить: на практике оценка A–C. С
оценкой D и хуже предодобрения нет — осторожный грейд уже в жёлтой зоне, заявку проверит человек.

Продукты стартапа (`startup_only` в products) предодобрение пропускает: выручки у стартапа нет,
предлагать не из чего, а продукт выдаётся только по заявке после предскрина. Вместо предложений
на главной кабинета стартап видит свой предскрин (bff, блок `startup.prescreen`).

Eligibility продукта, срок действия (30 дней) и хранение — в runtime модуля (#40).

## Тексты для клиента

подсказки и дозапрос: у `ClientDecisionDTO` этих полей нет совсем.

## Runtime: команды, события, API

**Консьюмер `decision.commands`** (group `decision.commands`):
- `MakeDecision` → `DecisionInputBuilder.collect` → `CreditPolicy.decide` → платёж оффера через
  `products.calculate_payment` (одна формула на систему) → запись в `decision_results` → outbox
  `DecisionMade {decision_id, outcome, offer?, decided_by, requested_info?, client_explanation,
  improvement_hints, alternative_product_code}`, `causation_id` = event_id команды. Оффер есть
  только у APPROVE (`as_requested`) и COUNTER_OFFER (`counter`), действует 7 дней. Повтор команды
  с тем же event_id — то же решение и тот же ответ, новой записи нет.
- `RecordManualDecision` — проверки андеррайтера: комментарий обязателен; APPROVE и COUNTER_OFFER —
  с условиями, REQUEST_INFO — с документами или полями, MANUAL_REVIEW вручную нельзя; сумма, срок и
  ставка — в рамках продукта из заявки; сумма ≤ полномочий `underwriter` 50 млн (выше — кредитный
  комитет). Нарушение → `ManualDecisionRejected {application_id, task_id, reason}`, решение не
  пишется. Успех → новая запись `decided_by=underwriter`, `override_of` = последнее авторешение
  (оно остаётся для аудита), проверки — в `rule_trace`, комментарий клиенту не уходит.

**Консьюмер `clients.events`** (group `decision.clients-events`): `FinancialReportSubmitted`,
`OrganizationVerified` и `OrganizationVerificationMismatch` (сверка с реестром могла сменить статус
или найти расхождение) → пересчёт предодобрений: по каждому активному продукту eligibility products
(не проходит — пропуск) → `scoring.estimate` без БКИ и выписок → `CreditPolicy.pre_approve` →
предложения на 30 дней, пересчёт перезаписывает все предложения компании →
`PreApprovedOffersUpdated {organization_id}`. Сид `backend/seed/decision.py` считает их для всех
демо-компаний тем же use case, без события (сид идёт на каждом старте).

**API** `GET /organizations/{id}/pre-approved-offers` — `organizations.read`; клиент видит только
свои компании (`clients.ensure_can(view)`, чужая — 404), сотрудник банка — любые. Действующие
предложения, крупные первыми, с оговоркой «предварительно, окончательное решение — после проверки».

**API предскрина учредителя** (ветка стартапа):

| Метод | Путь | Доступ | Что |
|---|---|---|---|
| POST | `/organizations/{id}/founder-prescreen` | `organizations.read`; клиенту — право подавать заявки от компании (`submit_application`), сотруднику банка — любая | запустить предскрин → 201; 422 `founder_not_found` / `consent_required`; 503 — БКИ не ответило |
| GET | `/organizations/{id}/founder-prescreen` | как у предодобрений | последний предскрин; 404 — ещё не было |

Ответ: `{status: passed | failed, founder: {account_id, name}, checked_at, valid_until, valid,
reasons: [{code, passed, message}]}`; `valid: false` — истёк, для заявки на `STARTUP` нужен новый.
Тот же предскрин bff берёт через `DecisionFacade.get_founder_prescreen`.

**Таблицы:** `decision_results` (решение неизменяемо; `sequence` — номер решения внутри заявки,
последнее = наибольший, даже при одинаковом времени; `requested_by_command` уникален —
идемпотентность; `triggers` и `rate_breakdown` — с `decision_0002`, расширенные лимиты — в JSON
`limits`), `decision_pre_approved_offers` (PK `organization_id, product_code`),
`decision_founder_prescreens` (с `decision_0003`: строка на каждую проверку, индекс
`organization_id, checked_at`, действует последняя).

Андеррайтер видит всё это в `GET /bff/backoffice/applications/{id}`: `scoring.segment`,
`scoring.pd_12m`, `scoring.reason_codes`, `scoring.ml` (оценка ML-модели), `decision.triggers`,
`decision.rate_breakdown`, `decision.limits.binding`, `decision.review` (`check` / `dispute` у
`MANUAL_REVIEW`). В очереди `GET /bff/backoffice/queue` у задачи — `review` того же смысла.

Тесты — `tests/decision/runtime/`: оба консьюмера через настоящие подписки и inbox, идемпотентность,
отказы ручного решения (без комментария, вне продукта, сверх полномочий), цепочка `override_of`,
права API, предодобрение пропускает неподходящие продукты, клиентский DTO без внутренних данных,
сид на настоящих clients, products и scoring. Предскрин — `test_decision_runtime_prescreen.py`:
срок 30 дней, причины отказа сохраняются, действует последний, без согласия в БКИ не ходим, нет
учредителя по реестру, БКИ не ответило — 503 и ничего не сохранено. Сквозной путь стартапа —
S-9 в `tests/scenarios`.

## Моки

Своих моков у decision **нет**: внешние данные приходят через `enrichment` (ЕГРЮЛ, ФНС, БКИ,
ГИР БО, Контур, БКИ руководителя, БКИ учредителя для предскрина — external-mocks за адаптерами),
выписки — синтетика `seed/statements`. Ключевая ставка
`DECISION_KEY_RATE` — синтетическое значение по умолчанию, не запрос к ЦБ.

## Упрощения

- Действует одна версия политики (`policy_v4`), выбор версии на заявку и сравнение версий на
  одной заявке — Could.
- Учредитель стартапа — руководитель по реестру: долей участников в данных нет, предскрин
  проверяет одного человека.
- Пороги матрицы, лимитов и компоненты ставки — стартовые синтетические, подобраны так, чтобы исходы
  демо S-1…S-8 не изменились.
- Залог оценивается по заявленной стоимости (оценка в моках — Could).
- Повторная проверка обязательных документов продукта (`INFO_MISSING_DOCUMENT`) не делается:
  комплектность проверяет applications при подаче.
