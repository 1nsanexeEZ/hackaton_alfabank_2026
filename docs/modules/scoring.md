# Модуль `scoring`

## Зачем

Отвечает на вопрос **«насколько рискованно дать деньги этому заёмщику»** — и объясняет почему. ТЗ
требует различать скоринг и кредитное решение: scoring даёт уровень риска, а продукт, сумму, ставку
и правила банка учитывает `decision`. Поэтому scoring **не знает** про ставки и лимиты, **не меняет**
статусы, его результат **воспроизводим** (по сохранённому входу и версии модели — тот же скор бит в
бит) и **объясним** (каждый фактор с вкладом — для андеррайтера и для подсказок клиенту).

ТЗ прямо допускает балльную модель вместо ML — берём **scorecard**: прозрачно, быстро, легко
защищать. Интерфейс `Scorecard.calculate` останется тем же, если позже рядом встанет ML-модель.

## Язык модуля

| Термин | Значение |
|---|---|
| Скор (`score`) | 0–1000, больше — меньше риск |
| Грейд (`grade`) | A (лучший) … E (худший) |
| Фактор (`Factor`) | признак и его вклад в баллах: «долговая нагрузка 0,52 → −10» |
| Флаг (`RiskFlag`) | сигнал для decision, не сводимый к баллам |
| Полнота данных (`data_completeness`) | доля факторов, по которым были данные |

## Агрегат

`ScoringResult` — неизменяемый; пересчёт = новая запись. Хранит `input_snapshot` (весь вход как
есть), `input_hash` (sha256 канонического JSON), `score`, `grade`, факторы, флаги, `data_completeness`
и `bank_notes` (пояснения банку, напр. про кассовый разрыв). Идемпотентность — по `requested_by_command`.

## Скоркарта из YAML

Логика факторов (как считаем значение и в какую корзину оно попадает) — в коде
(`domain/scorecard.py`); база, пороги грейдов и **баллы корзин** — в `infrastructure/config/scorecard_v1.yaml`.
Файл валидируется Pydantic-схемой при старте: нет фактора, корзины или не то число →
`ScorecardConfigError`, приложение не стартует (лучше сразу, чем молча посчитать не так).

## Факторы и итоговые веса

База **600**, итог зажимается в 0–1000.

| Фактор | Как считаем | Корзины → баллы |
|---|---|---|
| `business_age` | месяцы с регистрации | <12: −10 · 12–24: 0 · 24–60: +30 · >60: +50 |
| `revenue_trend` | выручка год к году | <−20%: −50 · −20…0%: −10 · 0…20%: +20 · >20%: +40 · нет данных: 0 |
| `debt_load` | (платежи БКИ + оценочный платёж по новому кредиту) / средняя месячная выручка | <0,2: +50 · 0,2–0,4: +10 · 0,4–0,6: −10 · >0,6: −100 |
| `bureau_overdue` | макс. просрочка 12 мес | 0: +40 · 1–30: −30 · 31–90: −120 · >90: −200 · истории нет: −10 (thin file) |
| `bureau_inquiries` | запросов за 30 дней | ≤2: 0 · 3–5: −15 · >5: −40 |
| `tax_arrears` | недоимка ФНС | 0: +10 · >0: −60 |
| `industry_risk` | секция ОКВЭД | low (62,63,69–74,86): +20 · mid: 0 · high (41–43,55–56,79): −30 |
| `amount_to_revenue` | сумма / годовая выручка | <0,1: +30 · 0,1–0,3: 0 · 0,3–0,5: −40 · >0,5: −40 |
| `revenue_consistency` | заявленная выручка vs ФНС | ≤15%: +10 · 15–30%: −20 · >30%: −60 (+ флаг) |
| `verification` | статус верификации | verified: +10 · mismatch: −30 (+ флаг) · иначе 0 |
| `collateral_coverage` | залог / сумма (для залоговых) | ≥2: +40 · 1–2: +20 · <1: 0 · нет залога — фактор не считается |
| `cash_gap` | прогноз кассового разрыва по выписке | разрыв: −15 (+ флаг и пояснение банку) · нет разрыва: +10 · выписки нет: 0 |

**Грейды:** A ≥ 750 · B 650–749 · C 550–649 · D 450–549 · E < 450.

**Калибровка.** `business_age`<12 → −10, `debt_load` 0,4–0,6 → −10, `amount_to_revenue`>0,5 → −40,
thin file → −10 без маршрутизации — чтобы молодой ИП с выпиской (S-2) оставался кандидатом на
встречное предложение, а не уходил сразу в ручную проверку.

**Нет данных** (источник упал или поля нет): фактор `points=0`, `direction=neutral`, отметка в
`data_completeness` и флаг (`bureau_unavailable`). Скоринг **не штрафует за наш же сбой** — решает
decision. Подсказки клиенту берём из 2–3 самых негативных факторов; конкретные числа модели клиенту
не показываем.

## Кассовый разрыв и подтверждение выручки

Фактор `cash_gap` берёт прогноз из снимка enrichment (`cashflow`): разрыв прогнозируется → −15, флаг
`cash_gap` и пояснение банку «по выписке прогнозируется кассовый разрыв в <месяц> на <сумму>». Если
оборот по выписке не подтверждает заявленную выручку (`revenue_confirmed=False`) — флаг
`revenue_mismatch` (как и при расхождении с ФНС).

## Воспроизводимость

`Scorecard.calculate` — чистая функция входа: без IO и без `now()` (возраст бизнеса и даты приходят
во входе). Вход сохраняется в `input_snapshot`, его sha256 — в `input_hash`. По снимку и версии модели
результат повторяется бит в бит (Replay — покрыто тестом).

## События

- Слушает `scoring.commands` → `CalculateScore {application_id}` (group `scoring.commands`).
- Публикует `scoring.events` → `ScoreCalculated {application_id, result_id, score, risk_grade, flags}`
  (`causation_id` = event_id команды), `ScoringFailed {application_id, reason}` — если снимка
  обогащения нет (считать не на чем).

## Фасад

- `get_result(application_id)` — последний результат для `decision` и карточки андеррайтера (bff).
- `estimate(company, amount=None)` — быстрая оценка без заявки и БКИ, ничего не сохраняет; для
  предодобрения. Допущения (чистая история, нет текущих платежей) — оценка ориентировочная.

## Внешние системы

Своих внешних интеграций и моков у scoring нет: ЕГРЮЛ/ФНС/БКИ и прогноз по выписке приходят из
`enrichment` через фасад, заявка и условия продукта — из `applications`.

## Упрощения

- Скоркарта синтетическая, откалибрована под демо; в проде заменяется/дополняется моделью на
  исторических данных банка (интерфейс `Scorecard.calculate` сохраняется).
- `estimate` принимает чистую кредитную историю по умолчанию — это ориентир, не решение.
- ML-модель (CatBoost по `docs/ml-guide.md`) — **Could**: на синтетике она лишь повторит правила.
