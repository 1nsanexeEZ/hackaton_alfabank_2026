# E2E-тесты кабинета клиента и рабочего места банка

Сквозные тесты интерфейса на [Playwright](https://playwright.dev): браузер проходит путь клиента так же, как жюри по разделу [«Что проверить за 10 минут»](../README.md#что-проверить-за-10-минут), и путь сотрудника банка в рабочем месте `/admin`. Сценарии S-1…S-10 из [README](../README.md#сценарии-проверки-s-1s-10) идут сквозь обе стороны: клиент подаёт заявку в мастере, андеррайтер в соседнем окне берёт задачу и решает её, клиент видит итог в открытой карточке без перезагрузки. Юнит-тесты логики фронта — в [`../frontend`](../frontend/README.md#тесты) (`npm test`).

## Запуск

Нужны Node.js 22+ и запущенный стенд: `docker compose up -d --build --wait` из корня репозитория.

```bash
cd e2e
npm ci
npx playwright install chromium   # один раз: браузер для тестов
npm test                          # все тесты, отчёт — npm run report
npx playwright test application-approved   # один файл
```

Стенд не отвечает на `/api/ready` — тесты сразу останавливаются с подсказкой, как его поднять. Проверка типов самих тестов — `npm run typecheck`. В CI (`.github/workflows/ci.yml`) e2e-тесты не запускаются: они ходят в уже поднятый стенд и создают на нём данные.

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `E2E_BASE_URL` | `http://localhost:8080` | адрес стенда |
| `E2E_DEMO_PASSWORD` | `Demo-2026!` | пароль демо-учёток, если на стенде другой `DEMO_PASSWORD` |

Стенд на другом порту — адрес задаётся переменной, в каждой оболочке по-своему:

| Оболочка | Команда |
|---|---|
| bash, Git Bash, macOS, Linux | `E2E_BASE_URL=http://localhost:8081 npm test` |
| Windows cmd | `set "E2E_BASE_URL=http://localhost:8081" && npm test` |
| PowerShell | `$env:E2E_BASE_URL="http://localhost:8081"; npm test` |

В cmd и PowerShell переменная живёт до закрытия окна: дальше хватит `npm test`. Кавычки в `set "…"` нужны — без них в адрес попадёт пробел перед `&&`.

## Посмотреть, как тест кликает

| Команда | Что видно |
|---|---|
| `npm run test:ui` | интерфейс Playwright: список тестов, запуск по одному, лента шагов со снимком страницы на каждом — куда кликнул, что ввёл, какие запросы ушли |
| `npm run test:ui:web` | то же в обычном браузере: откройте адрес из консоли, `http://127.0.0.1:9323` |
| `npm run test:headed -- application-approved` | тест идёт в живом окне браузера — быстро, S-1 проходит секунд за 15 |
| `npx playwright test application-approved --debug` | пошагово: тест встаёт на каждом действии, Playwright Inspector показывает, на какой элемент он нацелен |
| `npx playwright test --trace on`, затем `npm run report` | после прогона: в отчёте у каждого теста трасса с той же лентой шагов |

Упавший тест и без этого оставляет в `test-results/` скриншот, видео и трассу: `npx playwright show-trace <путь к trace.zip>`.

**Окно `test:ui` не открывается** с ошибкой `net::ERR_NETWORK_ACCESS_DENIED at http://[::1]:…` — антивирус или фаервол не пускают в сеть Chromium, который скачал Playwright. Запустите `npm run test:ui:web` и откройте адрес в своём браузере. Живое окно (`test:headed`, «Show browser» в UI-режиме) заработает, когда папка `%LOCALAPPDATA%\ms-playwright` будет в исключениях антивируса; обычный `npm test`, UI-режим в браузере и трассы от этого не зависят.

## Что проверяется

| Файл | Сценарий |
|---|---|
| `application-approved.spec.ts` | **S-1**: директор «Ромашки» из гостя входит по «Оформить заявку», подаёт «Кредит без залога» на 3 млн ₽ и 24 мес, получает автоодобрение, принимает предложение, скачивает проект PDF, принимает Правила и подписывает паролем. Видит подписи заёмщика и банка, скачивает подписанный PDF, открывает проверку по QR, сверяет файл — подлинный, а файл с одним изменённым байтом проверку не проходит |
| `application-rejected.spec.ts` | **S-4**: «Закат» получает отказ по стоп-факторам с объяснением и подсказками, действий по заявке нет |
| `underwriter-counter-offer.spec.ts` | **S-2**: ИП Иванов, 5 млн ₽ — модели видят умеренный риск, андеррайтер запрашивает выписку, клиент загружает CSV в карточке, андеррайтер видит прогноз кассового разрыва и предлагает 3 млн ₽, клиент видит «другие условия». **S-3**: «Вектор», кредитная линия на 10 млн ₽ — данные расходятся с ЕГРЮЛ, встречное предложение на 6 млн ₽ |
| `info-request.spec.ts` | **S-5**: «Прогресс» — банк сам запрашивает выписку, ответить без файла нельзя, клиент загружает её и отвечает, выписка не подтверждает выручку, андеррайтер отказывает |
| `underwriter-approval.spec.ts` | **S-6**: «Сбой» — БКИ не ответило, андеррайтер видит неответивший источник и одобряет. **S-7**: бизнес-ипотека на 30 млн ₽ с залогом, анкетой объекта и тремя документами — всегда у специалиста; ставку ниже коридора политика возвращает андеррайтеру с причиной, со второго решения — предложение |
| `accountant-signing.spec.ts` | **S-8**: бухгалтер двух компаний выбирает «Ромашку», подаёт и принимает предложение, но подписать не может; договор подписывает директор, бухгалтер видит выдачу |
| `startup.spec.ts` | **S-9**: без проверки учредителя «Далее» в мастере закрыто; учредитель даёт согласие и проходит проверку, андеррайтер делает проектную оценку, договор подписан, кредит выдан. **S-10**: бизнес-план и финмодель в «Компании», проектная оценка — «предодобрен кредит до …», заявка из предодобрения, андеррайтер подтверждает предзаполненную оценку, подпись и выдача |
| `workspace.spec.ts` | рабочее место: вход и выход, раздел без сессии ведёт на вход; обзор — показатели, период, настройка панели; очередь специалиста и все заявки, карточка с маршрутом и решением движка; проверка по ИНН; скоринг двух моделей; продукты (андеррайтеру — только просмотр, админу — ведение); модель и политика, примерка; ключевая ставка; андеррайтеру закрыты пользователи и роли, админ видит пользователей с поиском и матрицу прав |
| `landing.spec.ts` | лендинг гостем: первый экран, подбор продуктов под цель, пересчёт платежа, каталог из 9 продуктов и переход к расчёту, вопросы и ответы, 404, проверка договора по неизвестной ссылке |
| `login.spec.ts` | вход по телефону и паролю, ошибки формы, неверный пароль, учётка сотрудника на сайт не пускает, сессия после перезагрузки, выход |
| `cabinet.spec.ts` | профиль, компания (реквизиты, предодобрение, отчётность, участники, «Оформить» по предодобрению), уведомления, «Мои заявки» |
| `support.spec.ts` | вопрос в поддержку: проверка формы, чат, сообщение, закрытие обращения |
| `assistant.spec.ts` | умный помощник: гостя ведёт на вход, вошедшему отвечает на вопрос о платеже — по шаблону или от модели |

## Данные стенда

Тесты входят в демо-учётки кнопкой (`DEMO_LOGIN_ENABLED=true`, так compose поднимает стенд по умолчанию) и создают на стенде заявки, обращения и подписанные договоры. На публичном стенде они не пойдут: там сайт и демо-вход закрыты Basic Auth, а тесты его не передают.

У компании одна активная заявка на продукт. Поэтому перед каждым сценарием тест через API закрывает активные заявки своей компании по своему продукту: черновики и ждущие клиента отменяют, начатое подписание доводят до выдачи, а заявку, которая ждёт андеррайтера, решает демо-андеррайтер — берёт задачу и отказывает с комментарием «Закрыта перед e2e-тестом». Задачу, уже взятую демо-сотрудником (андеррайтером или админом), решает он же. Тест упадёт с номером заявки, только если задачу взял сотрудник не из демо-учёток: решите её в `/admin` и запустите снова.

Проверку учредителя «Старта» (S-9) сбросить через API нельзя, она действует 30 дней. Поэтому тест «без проверки заявку не подать» идёт на свежем стенде, а на стенде, где проверку уже прошли, пропускается с пояснением. Остальное в S-9 и S-10 идёт на любом стенде.

В мастере тест называет бенефициара так, как он записан в ЕГРЮЛ. Ответ «Никто» банк сверяет с реестром, видит расхождение и по 115-ФЗ отправляет заявку специалисту — автоодобрения S-1 тогда не будет.

## Как устроены тесты

- Элементы ищутся по ролям и подписям (`getByRole`, `getByLabel`), как их видит скринридер, — без `data-testid` и CSS-классов.
- Браузер запускается с `prefers-reduced-motion: reduce`: анимации входа и окон короткие, тест не ждёт их.
- Файлы идут по очереди в одном браузере: сценарии делят стенд и демо-компании.
- Клиент и сотрудник в одном сценарии — две страницы одного браузера: у сайта и рабочего места свои независимые сессии.
- `support/` — учётки, подготовка данных через API, общие шаги мастера заявки и подписи договора; `support/staff.ts` — вход сотрудника, очередь и решение по задаче; `support/global-setup.ts` проверяет `/api/ready` до первого теста.
- Документы заявки — маленький PDF из памяти; выписки по счёту — из сидов бэкенда `backend/seed/statements/`.
