# E2E-тесты кабинета клиента

Сквозные тесты интерфейса на [Playwright](https://playwright.dev): браузер проходит путь клиента так же, как жюри по разделу [«Что проверить за 10 минут»](../README.md#что-проверить-за-10-минут). Админку и рабочее место андеррайтера тесты не трогают.

## Запуск

Нужны Node.js 22+ и запущенный стенд: `docker compose up -d --build --wait` из корня репозитория.

```bash
cd e2e
npm ci
npx playwright install chromium   # один раз: браузер для тестов
npm test                          # все тесты, отчёт — npm run report
```

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `E2E_BASE_URL` | `http://localhost:8080` | адрес стенда; на другом порту — `E2E_BASE_URL=http://localhost:8081 npm test` |
| `E2E_DEMO_PASSWORD` | `Demo-2026!` | пароль демо-учёток, если на стенде другой `DEMO_PASSWORD` |

Стенд не отвечает на `/api/ready` — тесты сразу останавливаются с подсказкой, как его поднять.

- `npm run test:headed` — с окном браузера;
- `npm run test:ui` — пошагово в интерфейсе Playwright;
- `npx playwright test application-approved` — один файл.

Упавший тест оставляет в `test-results/` скриншот, видео и трассу: `npx playwright show-trace <путь к trace.zip>`.

## Что проверяется

| Файл | Сценарий |
|---|---|
| `application-approved.spec.ts` | **S-1**: директор «Ромашки» из гостя входит по «Оформить заявку», подаёт «Кредит без залога» на 3 млн ₽ и 24 мес, получает автоодобрение, принимает предложение, скачивает проект PDF, принимает Правила и подписывает паролем. Видит подписи заёмщика и банка, скачивает подписанный PDF, открывает проверку по QR, сверяет файл — подлинный, а файл с одним изменённым байтом проверку не проходит |
| `application-rejected.spec.ts` | **S-4**: «Закат» получает отказ по стоп-факторам с объяснением и подсказками, действий по заявке нет |
| `landing.spec.ts` | лендинг гостем: первый экран, подбор продуктов под цель, пересчёт платежа, каталог из 9 продуктов и переход к расчёту, вопросы и ответы, 404, проверка договора по неизвестной ссылке |
| `login.spec.ts` | вход по телефону и паролю, ошибки формы, неверный пароль, учётка сотрудника на сайт не пускает, сессия после перезагрузки, выход |
| `cabinet.spec.ts` | профиль, компания (реквизиты, предодобрение, отчётность, участники, «Оформить» по предодобрению), уведомления, «Мои заявки» |
| `support.spec.ts` | вопрос в поддержку: проверка формы, чат, сообщение, закрытие обращения |
| `assistant.spec.ts` | умный помощник: гостя ведёт на вход, вошедшему отвечает на вопрос о платеже — по шаблону или от модели |

## Данные стенда

Тесты входят в демо-учётки кнопкой (`DEMO_LOGIN_ENABLED=true`, так compose поднимает стенд по умолчанию) и создают на стенде заявки, обращения и подписанные договоры.

У компании одна активная заявка на продукт. Поэтому перед S-1 и S-4 тесты через API закрывают активные заявки «Ромашки» и «Заката» по «Кредиту без залога»: отменяют, а начатое подписание доводят до выдачи. Заявку, которая ждёт андеррайтера, клиент закрыть не может — тест упадёт с номером заявки; решите её в `/admin` и запустите снова.

В мастере тест называет бенефициара так, как он записан в ЕГРЮЛ. Ответ «Никто» банк сверяет с реестром, видит расхождение и по 115-ФЗ отправляет заявку специалисту — автоодобрения S-1 тогда не будет.

## Как устроены тесты

- Элементы ищутся по ролям и подписям (`getByRole`, `getByLabel`), как их видит скринридер, — без `data-testid` и CSS-классов.
- Браузер запускается с `prefers-reduced-motion: reduce`: анимации входа и окон короткие, тест не ждёт их.
- Файлы идут по очереди в одном браузере: сценарии делят стенд и демо-компании.
- `support/` — учётки, подготовка данных через API, общие шаги мастера заявки.
